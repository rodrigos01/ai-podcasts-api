# AGENTS.md

Guidance for AI coding agents working in this repository. Read this before making changes — several things here are non-obvious from the code alone.

## What this is

A REST API backend for an AI-generated podcast app: users create fictional podcast shows (hosts, structure) and episodes (topics, guests, source material), and the app generates an episode's conversation transcript via a single Gemini call, then synthesizes it to audio via Gemini TTS, streamed back to the client. Product behavior is specified in [specs.md](specs.md); the prompting conventions for TTS are in [prompting-guide.md](prompting-guide.md) and [voice-reference.md](voice-reference.md).

**specs.md is the product spec, not the API design.** It's silent on several things this backend had to decide — see "Architecture decisions" below before assuming specs.md is complete on its own.

## Migration from multi-agent to single-LLM script generation (2026-09-21)

Transcript generation used to be two independent LLM calls per turn (one `AgentSession` per speaker, alternating strictly, each with its own private system instruction) — replaced with **one LLM call that writes both speakers' lines itself** ([scriptGeneration.service.ts](src/services/episodeGeneration/scriptGeneration.service.ts), [scriptGeneration.prompts.ts](src/llm/prompts/scriptGeneration.prompts.ts)). This followed a real experiment comparing both approaches on the same live source material (methodology and full results are written up externally, not in this repo): single-LLM was 3.5-5.8x faster wall-clock and, contrary to expectation, produced *more* naturalistic turn pacing than forced per-turn alternation (shorter, choppier, more interruption-like exchanges — see "The conversational-density lesson" below). Two tradeoffs were consciously accepted, not overlooked:

- **No mid-generation word-count checkpoint.** The multi-agent loop's mechanical breaker (the old `conversationLoop.ts`) is gone — a single non-streaming call has no equivalent, and the experiment measured real overshoot (16-43% over target, worse under looser prompting, never fully eliminated by tightening it) because the model tends to track the source material's real scope over the literal word target. Mitigated at the product level instead: target length is now chosen *before* drafting (see point 8 below) and the episode wizard can suggest splitting into two episodes when the target is a genuine mismatch for the material — but there is still no hard guarantee on any single episode's transcript length. A real mid-generation checkpoint (stream the call, inject a forced wrap-up as word count nears the max) was considered and deliberately deferred, not rejected — worth revisiting if overshoot proves to be a real problem in practice.
- **No structural per-speaker knowledge partitioning.** The old pipeline gave each speaker an independent LLM call plus a per-speaker source split (`sourceAssignment.service.ts`, since deleted) so two speakers could never "know" something the other hadn't said aloud, by construction. A single LLM authoring both sides is unavoidably omniscient of everything in the prompt regardless of what the transcript shows — `scriptGeneration.prompts.ts` asks the model to keep the two characters' knowledge and reactions independent, but this is prompting, not a structural guarantee. Treat this as an accepted, permanent characteristic of this architecture, not a bug to fix later.

**Speaker labels are first name only, by contract, with the format validated (not fuzzily resolved) after generation (2026-09-22).** The experiment found stricter word-count prompting made the model drift between full names ("Maya Cruz") and abbreviated ones ("Maya") — since TTS voice assignment (today: `audio.service.ts`'s `resolveCastVoices` / `ttsClient.ts`) keys off the exact label string, this used to be handled by a fuzzy resolver (`normalizeSpeakerTurns`, trying exact → case-insensitive → prefix/first-name matching against the known cast) that guessed at what a drifted label "must have meant." That resolver is gone. Instead, [speakerSelection.ts](src/services/episodeGeneration/speakerSelection.ts)'s `speakerLabel(name, otherName)` computes one canonical label per speaker up front — first name only, falling back to the full name only when the two cast members share a first name — and [scriptGeneration.prompts.ts](src/llm/prompts/scriptGeneration.prompts.ts) tells the model to use exactly those two strings, framed as a hard technical requirement (byte-for-byte matching, not a style preference), not merely a naming convention. `scriptGeneration.service.ts`'s `validateSpeakerTurns` then does no resolution at all — it just checks that every parsed turn's label is one of the two expected strings and that both appear at least once, throwing (and letting the caller retry the whole generation — cheap, a single call) if not. The same `speakerLabel` computation is reused in `audio.service.ts`'s `resolveCastVoices`, so the transcript's turn labels and the TTS voice/speech-metadata mapping always agree on the same string. If you're tempted to bring fuzzy resolution back: don't — the whole point of the first-name-only convention is that the format is simple enough to ask for exactly and verify exactly, rather than needing to guess at variations.

**A real, independent bug this surfaced (2026-09-22): [scriptText.ts](src/utils/scriptText.ts)'s label-matching regex was ASCII-only** (`[A-Za-z0-9 .'-]`), so a genuinely correct label containing any accented or non-Latin letter (e.g. "Chloé") failed to match *at all* — not a drift/format issue, a parsing bug. The whole "Name: line" turn silently got folded into the previous turn's text as an unlabeled continuation, and the resulting missing speaker surfaced downstream as "the generated script never gives Chloé Moreau a line," which reads like a model-compliance failure but was actually this regex never recognizing her label in the first place. Fixed with Unicode property escapes (`\p{Lu}`, `\p{L}`, `\p{M}` for a possible NFD-decomposed accent) and the `u` flag on every `RegExp` built from `NAME_PATTERN` — this is a correctness fix independent of the first-name convention above (a first name can be accented too), so don't assume moving to shorter labels alone would have fixed it.

## Migration to Gemini 3.8 Flash TTS (2026-09-24)

Audio generation was fully replaced, moving off `@google-cloud/text-to-speech`'s `streamingSynthesize` (`gemini-3.1-flash-tts-preview`) onto Gemini 3.8 Flash TTS (`gemini-3.8-flash-tts`) — first via `@google/genai`'s AI Studio `interactions`/`voices` API, and since 2026-10-01 on the Gemini Enterprise Agent Platform's `generateContent`/Voices API (see the "Gemini Enterprise TTS" bullet below) — following a throwaway investigation spike (branch `claude/gemini-3.8-flash-tts-test-cphacd`, `scripts/test-gemini-3.8-tts.ts`) that found the new model sounds noticeably more natural and, crucially, doesn't need the old pipeline's chunking or director-prompt machinery at all. This is a large simplification, not a like-for-like swap — several things that used to be genuinely necessary are gone entirely:

- **Turn-based chunking with ADTS AAC streaming.** The pipeline breaks the episode into chunks bounded by turn count *or* word count, whichever is reached first (`chunker.ts`'s `chunkTranscript`, `TtsChunk`, `TURNS_PER_CHUNK` = 10, `MAX_WORDS_PER_CHUNK` = 650 — see `ttsLimits.ts`'s comments on both for the full reasoning). The word cap was added after discovering (2026-09-26) that `interactions.create` outright **rejects** a request whose synthesized audio would exceed ~300s, not just eventually time out — a fixed turn count doesn't bound audio duration at all (10 short backchannel turns vs. 10 long monologue turns produce wildly different lengths), so word count is used as a speech-rate proxy to keep each chunk's *estimated* duration safely under that ceiling before the request is even sent. This is the same content-size-bound principle the pre-3.8 Cloud TTS pipeline's deleted chunker used (there, token count, for a different technical ceiling) — reintroduced here for a different reason. A single turn whose own text alone exceeds the word cap is split into several same-speaker continuation chunks (`chunker.ts`'s `splitOversizedSpan`, preferring sentence-boundary cuts, falling back to a plain word-boundary cut for an unpunctuated run-on) rather than left as one over-limit chunk — unlike a genuinely ambiguous mid-transcript cut, there's no speaker to guess at here (it's still the same turn), so `getChunkTurns` just re-attributes a continuation piece to whichever speaker's label most recently appeared before it. Each chunk is synthesized via Gemini 3.8 Flash TTS on demand and encoded via ffmpeg to standalone ADTS AAC (`podcasts/.../chunk-{index}.aac`). Because ADTS frames are completely self-contained without container headers, AAC chunks are directly concatenable (`audio/aac`), eliminating the WAV header timeline/seeking bugs in players like ExoPlayer while reducing network egress bandwidth by ~90%.
- **No single-ogg finalization pass.** Instead of stitching and re-encoding all chunks to a single `final.ogg` after generation, the cached AAC chunks themselves are streamed directly. When all chunks are generated, `audioFinalize.service.ts` simply triggers `cleanupGuestVoice` to delete any temporary guest Voice-Design voices. Seeking (`Range` or `?t=`) works seamlessly across cached and live-generated AAC chunks.
- **Storage TTL**: `in-progress.wav` (7 days) and `final.ogg` (90 days) are meant to auto-expire — GCS has no true per-object TTL, so `audioCache.repository.ts` stamps `customTime` metadata at every write, and `scripts/configure-audio-storage-lifecycle.ts` (written but **not yet applied to the production bucket** — a human needs to run this deliberately) configures two `daysSinceCustomTime`-keyed bucket lifecycle rules to actually delete them.
- Two things still need live, billed manual verification before fully trusting this in production (this repo's testing philosophy — external APIs are verified manually, not mocked): `client.voices.delete()`'s exact behavior under real quota/error conditions, and the ~9,000-word `long`-episode ceiling mentioned above.
- **Gemini Enterprise TTS (2026-10-01): TTS runs on the same platform/credentials as text generation — no API key, no AI Studio.** It first shipped against the AI Studio API (`interactions.create` + `GEMINI_API_KEY` from Secret Manager) because the Enterprise endpoint rejected every call we made; that turned out to be two request-shape mistakes on our side, not a Google rollout gap (an earlier note here blamed a "partial rollout" — wrong). The authoritative source is `docs.cloud.google.com/gemini-enterprise-agent-platform/models/text-to-speech/{overview,voice-design}`; the code is `ttsClient.ts`, whose module comment repeats the two traps:
  - **Synthesis is `models.generateContentStream`, not `interactions.create`.** Parts carry `speechMetadata: { speaker?, style? }`; voices go in `config.speechConfig` (`voiceConfig.voice` for one speaker, `multiSpeakerVoiceConfig.speakerVoiceConfigs` — exactly two — for a dialogue); `responseModalities: ["AUDIO"]`. Streaming returns raw 24kHz mono 16-bit PCM (`audio/l16`), the same format the rest of the pipeline already consumed. `interactions.create` on Enterprise answers `400 Unsupported model interaction: gemini-3.8-flash-tts`.
  - **Voice Design needs `type: "VOICE_TYPE_PROMPTED"`** (the AI Studio-style `"prompted"` gets `400 Unsupported voice type.`), `store: true`, and must *not* set `voice.model` (`400 Model should not be set when store is true.`). Creation generates a sample (a few seconds, ~1,000 tokens billed) and transiently fails sometimes (`503`, or `400 Voice generation did not complete`) — a retry works, hence `designVoice`'s 4 attempts with 3s steps.
  - Models and the Voices API exist only in the **`global`** location (`ttsClient.ts` hardcodes it, as does `geminiClient.ts` — there is no location env var). Needs `@google/genai` >= 2.25.0 for the `speechMetadata` typings/serialization.
  - **Dropped vs. the AI Studio version:** `speech_config.mode: "conversational"` has no documented Enterprise equivalent, and the docs say nothing about the `|overlap|` backchannel syntax `scriptGeneration.prompts.ts` teaches — requests containing it are accepted and return audio, but nobody has confirmed by ear that it's rendered as overlap rather than ignored. The docs also say multi-speaker requests can't combine designed voices (synthesize turn-by-turn instead); a two-designed-voice dialogue request is accepted and was judged to sound the same as AI Studio's, so we send one request per chunk as before.
  - The Library path is gone: `findLibraryVoice` and the `TtsBackend`/Vertex-vs-AI-Studio probe were deleted (all voices are Voice Design — see `voiceResolution.service.ts`).
  - **Voice Design input is the name, the English bio and an accent line — nothing else, and no rewrite LLM call (2026-10-02).** Found by ear against the live API: the best prompt is just the speaker's bio in English (a voice designed from an English prompt still speaks any language, with the intended accent), and *stating* the accent explicitly is far more effective than leaving it to be inferred from the bio. So the wizard LLMs (`podcastWizard`/`episodeWizard`) now write `personaEn`/`accentEn` alongside `persona`/`accent` in the same request (identical copies when the show is already in English — `persona`/`accent` stay in the show's language for display and script generation), and `voiceResolution.service.ts`'s `designFor` sends `buildVoiceDesignInput(name, personaEn, accentEn)` (`Name: ...`, the bio, and `Accent: ...` if any, blank-line separated) as `prompted.input` — `display_name`/`gender`/`language_code` are optional and no longer sent (verified live). The free-text `voice` hint is no longer sent to Voice Design (it's display-only now, still required on the API for client compatibility; the old voice-design system prompt and its structured output are deleted). **The server writes the English fields itself at save time (2026-10-04)** — the wizards' output goes through a client that doesn't echo `accent`/`personaEn`/`accentEn` back (confirmed against Firestore: no stored person, old or new, has ever had an `accent`, let alone English fields; the server persists whatever the request body carries and nothing more). `personEnglish.service.ts`'s `withEnglishFields` therefore runs on every host at `POST /podcasts`, every guest at `POST .../episodes`, and (via `prepareHostsForUpdate`) every new or edited host on a podcast update: if a person lacks `personaEn` (or has an `accent` but no `accentEn`), one small `generateText` call (`translateForVoice`) fills them in from the persona **and the voice hint** — the wizards usually describe an accent only in the hint and leave `accent` empty, so `accentEn` is derived from whatever the text states (never from origin alone) and is independent of the `accent` field. Best-effort: on failure the person is saved as-is. The English fields stay optional in `personInputSchema` (a client may send its own), and `englishInputFor` in `voiceResolution.service.ts` still translates on demand for anyone saved without them. On a host update, `utils/englishFields.ts`'s `reconcileEnglishFields` keeps stored English fields when the client omits them and nothing changed, and drops both when the persona, voice hint or accent changed (they derive from all three) so fresh ones get written. An *untouched* legacy host is deliberately left without English fields on update — adding them would change its `voiceHash` and trigger a pointless re-design. `voiceHash` appends the English fields only when present, so every voice stored before this change stays valid (no mass re-design); the cost is that editing the now-unused `voice` hint still re-designs once. The name is sent first because a bio doesn't always make gender clear.
  - **The Voice Design prompt is stored on the person as `voicePrompt` (2026-10-05).** It's `buildVoiceDesignInput(name, personaEn, accentEn)`, built by `personEnglish.service.ts`'s `withVoicePrompt` (which writes the English fields first if missing, falling back to the original persona/accent if that fails). The wizard responses add it per host/guest (the wizard LLM never writes it — it's in `personSaveSchema`, not the LLM-facing `personInputSchema`), confirm saves it, host edits keep/drop/rebuild it via `reconcileVoicePrompt` (a name change also makes it stale, since it opens with the name), and `voiceResolution.service.ts`'s `designFor` designs from it, writing and persisting it first when a person has none. It deliberately does **not** feed `voiceHash`. `POST /voices/design` (public preview at `GET /voices/:voiceId/preview`) lets clients design 3 candidates per prompt under a `sessionId` (wizard-minted, or the podcast/episode id when editing), registered in the `designedVoices` collection.
  - **Picking a designed voice on save (2026-10-05).** Clients send the picked voice as the person's existing `resolvedVoiceId` (optional on `personSaveSchema`; `resolvedVoiceOrigin`/`Hash` stay server-managed) on `POST /podcasts` and `POST .../episodes` (plus a body `sessionId`, the wizard's) and on `PATCH /podcasts/:id` hosts / `PATCH .../episodes/:id` guests (session = the podcast/episode id). `voiceSelection.service.ts`'s picker only honours an id that is one of the caller's *unlinked* candidates in that session; anything else (unknown, stale, the person's own current voice echoed back, no session) is treated exactly as if no id was sent, i.e. the lazy design-at-generation path. `utils/voiceDecision.ts`'s `decideVoice` is the pure rule: a pick is stored with `resolvedVoicePinned: true` and the *prompt it was designed from* (so the stored prompt always describes the stored voice); with no pick, a changed `voicePrompt` drops the stored voice (designed lazily from the new prompt; a person stored without a prompt is never touched — the hash covers them); otherwise untouched. A pinned voice is valid regardless of `voiceHash` (`hasCurrentVoice`), a pinned guest is not re-designed on `/regenerate` and not deleted by `cleanupGuestVoice` — it's deleted with its episode. After the response the picker links the applied picks (`designedVoices.linked`, so later cleanups of the same session id never touch them), then deletes every other unlinked candidate in the session plus any stored voice the save replaced, best-effort. Cleanup in an edit only runs when hosts/guests are in the body. Deleting a podcast/episode deletes its hosts' voices and picked guest voices. **Hosts a `PATCH /podcasts/:id` leaves without a voice (new, or the stored voice was dropped because the prompt changed) get one designed in the background right after the save** (`needsVoiceNow` / `designHostVoicesNow`), so the next generation finds it ready; the lazy design at generation stays as the fallback, and untouched hosts are never designed on a save. Guests deliberately aren't: a guest's voice is per-generation (re-designed on `/regenerate`, deleted after audio finalizes), so designing one at PATCH would mostly be thrown away. **Not done:** cached audio isn't purged when a voice changes (an episode caught partly cached plays old and new voices), and nothing sweeps sessions that were abandoned without a save.
  - **Stored `voice_...` ids are per-platform, so every stored voice carries a version-salted hash.** Voices designed on AI Studio don't exist on Enterprise. `voiceResolution.service.ts`'s `voiceHash` mixes `VOICE_BACKEND_VERSION` into name/persona/accent/hint, hosts *and* guests record it in `resolvedVoiceHash`, and `hasCurrentVoice(person)` (id present AND hash matches) is the single check `resolveCastVoices` uses — anything else is re-designed lazily on first live synthesis. So a pre-migration host or guest gets a fresh voice the first time a not-yet-cached chunk is needed; bumping `VOICE_BACKEND_VERSION` invalidates every stored voice the same way for any future platform move. A guest voice with a null hash (pre-migration) is *not* deleted when it's replaced (it's foreign; the delete would only fail). `resolveCastVoices` runs only on the live-generation path, after the all-cached fast path — replaying a fully cached episode never designs a voice. **Known, accepted consequence:** an episode caught partly cached across the migration plays its cached chunks in the old voices and the rest in newly designed ones (Voice Design is non-deterministic, so the voices audibly change at that chunk boundary); nothing records which voice made which cached chunk. `/regenerate` is the way to get a consistent episode.
  - **Leftover infra to clean up by a human** (nothing here is done from an agent session): the `gemini-api-key` secret in Secret Manager and its two `secretAccessor` bindings are now unused. `deploy.yml` passes `--remove-secrets GEMINI_API_KEY` so Cloud Run revisions stop referencing it; delete the secret itself only after that has deployed to every service. The runtime service account (`883622140264-compute@...`) needs permission to call the Voices API and `generateContent` for TTS — it already runs text generation through the same platform with `roles/aiplatform.user`, which should cover it, but this has only been verified from the `player@` service account.

## Continuity: full transcript history, not condensed summaries (2026-09-29)

Script generation and the episode wizard (draft *and* revise) are given the **full transcripts of up to `MAX_HISTORY_EPISODES` (15, [constants/episodeHistory.ts](src/constants/episodeHistory.ts)) earlier episodes**, replacing the per-host condensed summaries (`condensation.service.ts`, `condensedSummaries`, and its extra LLM call per episode were deleted — old episode docs may still carry the field; it's ignored). ~15 long episodes is ~180k tokens, well inside Gemini 3.8 Flash's 1M window. Transcripts only, deliberately: sources roughly double the size and what the hosts actually *said* is what continuity depends on.

- **"Previous", not "latest".** The window is the (up to) 15 episodes strictly *before* the episode being generated, ordered by `(createdAt, id)` — see `utils/episodeHistory.ts`'s `selectPriorEpisodes`. `createdAt` is written once in `createEpisode` and never changes on regenerate/PATCH (only `updatedAt` does), so regenerating episode N sees N-15..N-1, never episodes written after it. `id` is only a tiebreaker (a confirmed 2-part split creates both episodes in the same loop). There is deliberately no explicit sequence field. The wizard has no episode yet, so its window is simply the latest 15.
- Only episodes with a non-null `transcript` count. Later episodes are *not* regenerated when an earlier one is, so they can drift from its new version — accepted.
- The history block ([llm/prompts/episodeHistory.prompts.ts](src/llm/prompts/episodeHistory.prompts.ts)) is at the front of the system instruction, so a generation's retries share a prompt prefix. Each header carries the episode's series number, title, and cast.
- With no condensation pass, generation goes straight from `generating` to `ready`; `"streamable"` remains in the status enum only for clients/old docs.

## Architecture decisions not in specs.md

These were made explicitly during development and should be treated as settled unless the user says otherwise:

1. **Firebase Auth is required** (reversed from an earlier "no auth" decision made before the client side existed). Every `/podcasts` route (and everything nested under it) requires a Firebase Auth ID token — see [middleware/requireAuth.ts](src/middleware/requireAuth.ts), which verifies it via `getAuth(firebaseApp).verifyIdToken()` and attaches `req.userId`. Podcasts are scoped by an `ownerId` field set at creation time; [services/podcastAccess.ts](src/services/podcastAccess.ts)'s `requireOwnedPodcast` is the one shared authorization check used by every controller nested under a podcast (sources, episodes, audio) — a podcast that exists but isn't yours is treated identically to one that doesn't exist (404, never 403), deliberately not leaking existence. This backend still uses the Admin SDK exclusively (bypasses Firestore security rules), so `firebase.rules` (gitignored, not in this repo checkout) is enforcing nothing — all authorization happens in application code, and it must mirror what those rules describe (`isOwner` there is the same model as `requireOwnedPodcast` here). `/health` and `/voices` are intentionally left public. The one exception to "auth via header": `.../audio/stream` also accepts `?token=<idToken>` as a query param, since a plain `<audio src>` element can't attach custom headers and specs.md requires that endpoint to work with one.
2. **Firestore subcollections**, not the nested arrays specs.md literally describes: `podcasts/{id}/episodes/{id}` and `podcasts/{id}/sources/{id}` are subcollections. Hosts stay **embedded** on the podcast document (small, bounded ~1-6) — only episodes and sources (unbounded, large text blobs) moved out, to avoid Firestore's 1MiB per-document limit.
3. **Firestore uses a named database, not `(default)`**: set via `FIRESTORE_DATABASE_ID` (currently `podcasts`). See [src/config/firebase.ts](src/config/firebase.ts) — `getFirestore(app, databaseId)`. If you add a new Firestore database or switch projects, this must be created explicitly (`firebase firestore:databases:create`) — it does not exist by default.
4. **Async job pattern for episode generation**: confirming a suggestion returns `202` immediately with every created episode at `status: "generating"`; script generation runs fire-and-forget in-process (no queue/Redis) — see point 8 below for how a 2-episode confirm is sequenced. Unlike the old per-turn pipeline, the transcript is **not** persisted incrementally — it's written by one LLM call ([scriptGeneration.service.ts](src/services/episodeGeneration/scriptGeneration.service.ts)) and only patched into Firestore once that call (plus parsing/normalization) succeeds — see [orchestrator.ts](src/services/episodeGeneration/orchestrator.ts). This means a crash mid-generation now loses the whole not-yet-persisted script, not just an in-flight turn — an accepted tradeoff of the single-LLM migration (see above), not an oversight. There is no automatic resume — `POST .../episodes/:id/regenerate` restarts a single episode from scratch. If you're asked to add real resume-from-partial or a mid-generation checkpoint, that's a legitimate gap, not an oversight. **`/regenerate` works on an episode at any status, including `"ready"`** (2026-09-26 — previously blocked with a 400 once an episode reached `"ready"`, which turned out to be actively wrong once chunking/prompt changes meant an already-"ready" episode was often exactly the one worth regenerating, and a user may simply want a different take on the same material). `runEpisodeGeneration`'s first real step is resetting the episode back to a clean slate — `status: "generating"`, `transcript`/`ttsChunks`: `null`, `generatedAudioSeconds: 0`, and a `storage/audioCache.repository.ts`'s `deleteEpisodeAudio` call clearing every cached chunk file — before touching anything else. This isn't just tidiness: without it, a listener hitting `/stream` in the window between accepting a regenerate request and the new script landing would still see the *old* transcript (`assertAudioAvailable` only blocks on a null transcript or `status === "failed"`, not on `"generating"` by itself) and could even become a chunk-generation leader synthesizing audio for content about to be discarded — wasting a real, billed TTS call. Clearing the cached chunk files matters independently of that race: a new attempt's chunk boundaries/count won't line up with the old ones, so a stale file left at the same index could otherwise get served (or mistaken for "already cached") against entirely different content. `status` has four values, not three: `"generating"` → `"streamable"` → `"ready"` (plus `"failed"`). The orchestrator flips `"generating"` to `"streamable"` as soon as the script itself is written — clients polling `GET .../status` should treat `"streamable"` the same as `"ready"` for "go ahead and call `/stream`" (audio generation is entirely `/stream`'s own job now, not something the orchestrator prepares — see the Gemini 3.8 Flash TTS migration section above), and only look for `"ready"` when they specifically need the episode fully finished (e.g. before trusting `condensedSummaries`, or full-seek support once `/stream`'s static-resource fast path kicks in).
5. **Orchestration is script generation + voice resolution (run in parallel) — the streaming synthesis call itself still has no generation-time step.** Since the Gemini 3.8 Flash TTS migration (see above) removed both the director/producer prompt and chunking, `orchestrator.ts` has nothing audio-*synthesis*-related to do between the script coming back and flipping status to `"ready"`: no `producerPrompt.service.ts` call, no `chunkTranscript` call, no `ttsPrompt`/`ttsChunks` state. It does, however (as of 2026-09-25 — see the voice-resolution note above), resolve and persist both cast members' TTS voices, in parallel with the script-generation call, so that work is off the critical path to first audio byte. The streaming synthesis call, WAV caching, and Ogg finalization still happen lazily, entirely inside `audio.service.ts`, the first time a listener's `/stream` request actually needs them (see that section below) — only voice resolution moved earlier.
6. **Stateless wizards**: the server persists nothing until final confirm (`POST /podcasts` or `POST .../episodes`). The client round-trips the current draft/options (or, for episodes, the full `suggestions` array — see point 8) payload on every revision call. Confirming is the one place an episode wizard payload does carry structure server-side: `POST .../episodes` takes `{ episodes: [...] }` (1 or 2 entries — a whole suggestion, not a single draft) precisely so the server can create and sequence a split as one unit instead of the client having to orchestrate it.
7. **The episode "2 voices" rule is a hard, always-enforced constraint**, not a default: `participantHostIds.length + guests.length` must equal exactly 2 (zod `.refine` in [episode.schema.ts](src/schemas/episode.schema.ts)). A single-host podcast therefore requires a guest on *every* episode — there is no solo-host mode, and a podcast with >2 hosts requires the client to pick which 2 voices are cast per episode. This is unaffected by the multi-agent-to-single-LLM migration above or the Gemini 3.8 Flash TTS migration — it's a product decision about how many voices an episode casts, independent of how the transcript is authored or which TTS backend synthesizes it.
8. **Episode length word ranges** (specs.md left `long`'s minimum unstated): short 3500-5000, medium 6500-8000, long 8000-9000 — see [constants/lengthRanges.ts](src/constants/lengthRanges.ts). `length` is now chosen by the client on the **first** episode-wizard request (`POST .../episodes/wizard/options`), before any draft is generated, not suggested afterward — there is no more `suggestedLength` output hint (removed 2026-09-21; it briefly existed 2026-09-20 as a post-hoc hint before this change). The wizard's response is always an array of 1-2 `suggestions` ([wizard.schema.ts](src/schemas/wizard.schema.ts)'s `episodeWizardOptionsResponseSchema`), and **each suggestion is independently either a single episode or a 2-episode split — there is no positional convention** (e.g. no "suggestions[0] is always the single-episode option"). A suggestion's shape is fully described by its own `episodes.length`; clients must key off that, never array position. A lone suggestion can itself be a split (e.g. the user's own prompt explicitly asked for the material to be split, or the material is a genuine mismatch for the chosen length) with no separate single-episode option offered at all; a second suggestion, when the drafter includes one, is just a genuinely useful alternative worth presenting side by side (e.g. a tight single episode vs. a fuller two-part treatment) and is *not* required to differ in episode count from the first. This went through two earlier, wrong designs worth knowing about if you touch this again: first a `.check()` refinement in `wizard.schema.ts` hard-rejected any response that didn't match an assumed "entry 0 has exactly 1 episode" convention — broken because that cross-entry rule can't be expressed in Gemini's structured-output schema, so the model routinely violated it (especially on revise) and every violation failed the whole request. That was replaced with a code-level repair step (`episodeWizard.service.ts`'s `normalizeSuggestions`, since deleted) that silently reordered/synthesized suggestions back into the assumed convention — which fixed the crash but was itself wrong, since it *forced* a single-episode option into existence even when the model correctly decided a split was the only sensible suggestion. The current design has no convention left to enforce or repair: `generateSuggestions`/`reviseSuggestions` just return the schema-validated result directly. **Confirming a suggestion (`POST .../episodes`) always takes its whole `episodes` array in one call** ([episodeCreateRequestSchema](src/schemas/episode.schema.ts), `{ episodes: [...] }`, 1 or 2 entries) — not one draft at a time. The controller creates every episode in the array immediately (all returned in the response, all at `status: "generating"`), then hands their ids to `orchestrator.ts`'s `runEpisodeGenerationSequence`, which actually generates them **one at a time, in order**: part 2's script-writing call doesn't start until part 1 reaches `"ready"`, so it sees part 1's transcript in its history window the same way any other follow-up episode would. This sequencing is entirely server-side and transparent to the caller — a client never orchestrates it, and confirming a single-episode suggestion (`{ episodes: [oneDraft] }`) goes through the exact same code path with a 1-element array. If an earlier part in the sequence fails, `runEpisodeGenerationSequence` marks every remaining part `"failed"` too (with an explanatory `error`) rather than leaving them stuck in `"generating"` forever — `/regenerate` still works on any one of them individually afterward. There is deliberately no persisted link between the parts of a split (no `partOf`/`seriesId` field on `Episode`) — grouping is conveyed only through each draft's own title/topics/productionNotes text, and the confirm request's array order.
9. **Firebase Storage bucket must be explicitly linked** to the Firebase project — creating a GCS bucket and pointing `firebase-admin`'s Storage client at it (via `storageBucket` in `initializeApp`) works at the SDK level but does **not** make it appear in the Firebase console's Storage tab. That requires the `firebasestorage.googleapis.com` API to be enabled on the project and the bucket registered via its bucket-management REST API (`POST .../buckets/{bucket}:addFirebase`). Already done for the current bucket (`ai-audio-book-podcast-audio`); if you provision a new bucket, repeat this.

## The conversational-density lesson (read before touching script-generation prompts)

Early testing (on the old per-turn, two-independent-agent pipeline) found that generated transcripts read as a "two-way monologue" — each turn a complete, thorough response — regardless of topic (audio gear, celebrity gossip, marine biology) or format (2 co-hosts, host-interviews-guest). That ruled out topic/format as the cause. The fix was explicit persistent guidance that most turns should be short (a reaction, an interjection, a partial thought), that a turn can be a pure reaction with zero new information, and that a speaker can deliberately leave something unfinished as a hook for the other to ask about — this guidance now lives in [scriptGeneration.prompts.ts](src/llm/prompts/scriptGeneration.prompts.ts)'s `buildScriptSystemInstruction` (carried over from the old per-speaker `hostPersona.prompts.ts`, since deleted). **Do not add example phrases to that guidance** — the user explicitly asked to avoid them since concrete examples bias the model toward reusing those exact words. Interestingly, the single-LLM migration's own experiment found this same guidance produces turns that are *shorter and choppier* than the old forced-alternation pipeline ever managed — a single writer, unlike two independent agents taking strict turns, can freely decide how many turns one "beat" takes instead of front-loading a whole beat into one turn because it doesn't control when it speaks again.

**A real bug from the old pipeline (2026-09-19, still relevant): dialogue occasionally started a new paragraph/line with something shaped like a speaker label** — e.g. "Watch this: it does something wild". `transcriptBuilder.ts` joins turns with `"\n\n"`, and everything downstream (`scriptText.ts`'s `parseScriptTurns`, the sole consumer now that chunking is gone — see the Gemini 3.8 Flash TTS migration section above) re-splits on that exact separator to find turn boundaries — so a line landing on "Word:" got misread as a new speaker label, scrambling TTS voice attribution. Still fixed two ways, deliberately not just one: `scriptGeneration.prompts.ts`'s system instruction explicitly tells the model not to open a line (or an internal sentence) with "word:" phrasing, *and* `scriptGeneration.service.ts`'s `sanitizeTurnText` unconditionally collapses any internal `\n{2,}` within a parsed turn's own text into a single space — so the invariant ("a turn's text never contains the turn-boundary separator") holds regardless of whether the model actually complies with the prompt. Don't remove the code-level collapse just because the prompt instruction seems to be working.

**A fourth lesson (2026-09-20, still relevant): agents defaulted to ending most turns with a question** — a recognizable "LLM interview" tic (always fishing for the other speaker's next line rather than just... talking) rather than how real co-hosts actually converse. Fixed with an explicit instruction not to close every turn with a question, while still allowing occasional genuine ones, with one carve-out: a show whose structure/production notes actually call for an interview format should keep asking questions, since that's the correct dynamic there. Verified against a real episode generation on the old per-turn pipeline (co-hosting, not an interview): only 2.2% of turns ended in a question mark — comfortably in "occasional and natural" territory, not the "every turn" pattern that prompted the fix. Re-verify this hasn't regressed if you touch `scriptGeneration.prompts.ts`'s question-ending guidance, since it's now one writer deciding for both speakers rather than two independent agents each separately instructed.

## Gemini API usage — non-obvious things learned the hard way

- **Text generation** (`gemini-3.8-flash`) uses the **Interactions API** (`client.interactions.create`) — `generateContent` remains supported but isn't used for text. Structured output is `response_format: <JSON schema>` built from the same zod schema used to re-validate the output (`toGeminiSchema` in [geminiClient.ts](src/llm/geminiClient.ts) still strips `$schema`/`additionalProperties`; that was needed by the old `responseSchema` dialect and is kept only because it's known-good — a raw zod schema was also accepted when probed 2026-10-01), and the result is read from `interaction.output_text` after checking `status === "completed"` (an `"incomplete"` status, e.g. output cut off at the token limit, is thrown rather than returned as if it were whole). Never trust LLM JSON without the zod re-parse.
- **Text generation is routed through the Gemini Enterprise Agent Platform API (Google's current name for what used to be called Vertex AI), not the API-key-based Generative Language API ("AI Studio")** (migrated 2026-09-20; renamed in SDK terms 2026-10-01). `getClient()` in [geminiClient.ts](src/llm/geminiClient.ts) constructs `GoogleGenAI` with `{ enterprise: true, project: env.FIREBASE_PROJECT_ID, location: "global", googleAuthOptions }` instead of `{ apiKey }`. The Interactions API only serves `global`, so the location is a constant, not an env var. **Every text call sets `store: false`**: Interactions are retained server-side for 7 days by default, and our prompts carry users' source material while the responses are whole transcripts; stateless mode is zero-data-retention and nothing here chains with `previous_interaction_id`. `enterprise: true` is the SDK's current recommended flag; the older `vertexai: true` still works (same `aiplatform.googleapis.com` endpoint) but the SDK's own types now point callers at `enterprise` instead, so this codebase uses that one. Motivation for being on this API at all (vs. AI Studio) was billing, not quality or capability: AI Studio bills through a separate, pre-paid path, while this bills the same GCP project (standard metered billing, `roles/aiplatform.user` required on the service account) that Firebase Admin already uses. TTS (`llm/ttsClient.ts`) is a separate client on the same platform and credentials — see the "Gemini Enterprise TTS" bullet in the Gemini 3.8 Flash TTS migration section above.
- **Structured output (`responseSchema`, then `response_format`) is real overhead, not free — use `generateText` only when the shape genuinely needs validating.** Confirmed empirically on the old `generateContent` `responseSchema` path (2026-09-17, 15 real side-by-side trials against the live API with an equivalent short prompt/response; not re-measured on Interactions): grammar-constrained JSON output ran ~35-55% slower on average than the same call with no schema at all, with a noticeably fatter slow tail (the multi-second outliers were structured-only). The episode script writer ([scriptGeneration.service.ts](src/services/episodeGeneration/scriptGeneration.service.ts)) doesn't need JSON — its output is just the "Name: line" transcript text itself, parsed by `scriptText.ts`'s `parseScriptTurns` — so it uses `generatePlainText` instead. The wizards/`voiceResolution.service.ts` still use `generateText` — their shapes are complex enough that hand-parsing plain text would be more fragile, not faster in any way that matters relative to their call frequency.
- **`@google/genai`'s type declarations trip up TypeScript's Node16/NodeNext module resolution** for a plain `import`/`require` (shared `types` field across import/require conditions in its `package.json` exports map, and the package is ESM-first). The fix in use, in both `geminiClient.ts` and `ttsClient.ts`: a dynamic `import("@google/genai")` inside the client-getter function, plus a type-only import guarded with `with { "resolution-mode": "import" }`. Don't "simplify" this back to a static import without re-testing `tsc --noEmit`.
- **TTS-specific findings (voice resolution, streaming synthesis, the WAV→Ogg finalize step) are documented in the "Migration to Gemini 3.8 Flash TTS" section above and in [ttsClient.ts](src/llm/ttsClient.ts)'s own comments** — the Cloud TTS-era findings that used to live in this section (speaker-alias constraints, per-chunk `RST_STREAM` ceiling, single-speaker/multi-speaker voice config bugs, cross-instance chunk-generation locking) described code that's now entirely deleted (`streamSpeech`, `chunker.ts`, `utils/oggStitch.ts`, `utils/oggOpus.ts`) and are no longer relevant to the current pipeline.

## Other gotchas

- **`pdf-parse` v2's API is class-based** (`new PDFParse({ data: buffer }).getText()`), not the v1 `pdf(buffer)` function — don't follow v1-era examples. Use `result.pages[].text` joined with `\n\n`, not `result.text`, which includes ugly `-- N of M --` page markers.
- **`firebase-admin` v14 wants the modular API** (`initializeApp`/`getFirestore`/`getStorage` from `firebase-admin/app`, `/firestore`, `/storage`), not the old namespaced `admin.initializeApp()` style.
- **`dotenv` v17 prints random self-promotional "tips" to stdout on load.** Not a compromise, just noise — suppressed via `dotenv.config({ quiet: true })` in [config/env.ts](src/config/env.ts). Don't reintroduce a bare `import "dotenv/config"`.
- **TypeScript here is v7** (the newer compiler); `moduleResolution` only accepts `node16`/`nodenext`/`bundler` — `"node"` (classic) is gone. This repo uses `module: "Node16"` + `moduleResolution: "Node16"`, which still allows extensionless relative imports for CommonJS output (no `.js` suffix needed), unlike a straight ESM setup.
- **Compound Firestore queries mixing `array-contains` with `orderBy` on another field need a manually-provisioned composite index.** `getPriorEpisodes` in [episode.repository.ts](src/data/episode.repository.ts) deliberately filters in memory instead, to avoid that operational dependency — fine at this app's expected scale (episodes per podcast).
- **Firestore rejects `undefined` field values outright** (throws, doesn't silently drop them). Any optional field must be omitted via spread (`...(x ? {field: x} : {})`), never set to `undefined`.
- **`npm run build` uses [tsconfig.build.json](tsconfig.build.json), not the root `tsconfig.json`, on purpose.** The root config's `rootDir: "."` + `include: ["src", "scripts", "test"]` (so `tsc --noEmit` also typechecks scripts/tests) means a plain `tsc` build emits to `dist/src/index.js`, not `dist/index.js` — silently breaking `npm start`/a deployed container's entry point (`"main"`/`"start"` in package.json both assume `dist/index.js`). This went undetected for a while because local dev always used `tsx` directly, bypassing `tsc` output entirely; it only surfaced when actually deploying. `tsconfig.build.json` narrows `rootDir`/`include` to `src/` only, so `npm run build` produces the right layout. If you ever see "Cannot find module '.../dist/index.js'" after a build, this is almost certainly why.
- **Google Drive sources ([googleDrive.service.ts](src/services/googleDrive.service.ts)) call the Drive v3 REST API directly with plain `fetch`, no `googleapis` SDK** — it's just two GET calls (metadata, then export-or-download), and the caller's own OAuth `accessToken` goes straight through as the `Authorization: Bearer` header; this backend never has Drive credentials of its own and never persists that token. Confirmed empirically against the real API (not assumed from docs): an invalid token genuinely comes back `401` from Drive, and it's mapped to our own `401` rather than leaking Google's error JSON shape — same for `403`/`404`. Google Docs (`application/vnd.google-apps.document`) must be exported (`/export?mimeType=text/plain`); the raw `alt=media` download only works for already-binary files like PDFs (`extractPdfText` reused unchanged). Any other mimeType is rejected with `400`. Like `geminiClient.ts`, this has no automated tests — it's a thin wrapper around a real external API, verified manually (only the error-mapping path is practical to verify without a real Drive OAuth token in hand; the Docs-export and PDF-download success paths still need a real token + file to confirm against, not yet done).

## Audio delivery (`/stream`)

`GET /podcasts/:podcastId/episodes/:episodeId/audio/stream` serves an episode's audio, generated entirely on demand — there is no generation-time audio step at all (see the Gemini 3.8 Flash TTS migration section above). See [audio.service.ts](src/services/audio.service.ts) for the full logic; the short version:

- **The gate is `assertAudioAvailable`, not "episode status is ready."** It only rejects `status: "failed"` or a missing `transcript`. A `"streamable"` or `"ready"` episode (a transcript exists) can always have its audio generation started; a `"generating"` episode with no transcript yet has nothing to serve and is rejected the same as `"failed"`.
- **If `final.ogg` already exists in Storage** (a prior request already generated and finalized this episode's whole audio): serves it as a normal static resource — real `Content-Length`, `Accept-Ranges: bytes`, honors a real `Range` request with `206`/`Content-Range`, full seek support, via `createFinalAudioReadStream`. No custom offset bookkeeping needed — it's one complete file, not stitched fragments.
- **Otherwise, chunk-by-chunk on-demand synthesis**:
  1. Reads both cast members' `resolvedVoiceId` — normally already persisted by `orchestrator.ts` at generation time (see the 2026-09-25 voice-resolution note above).
  2. Iterates over `ttsChunks` (or chunks the transcript on the fly if needed):
     - For already-cached chunks (`chunk-{index}.pcm`), streams them directly to the client, skipping or slicing to match any seek position (`?t=` or `Range`).
     - For the first un-cached chunk, seamlessly transitions to live generation: acquires the chunk lock (`data/audioLock.repository.ts`'s `tryAcquireChunkLock`), calls `streamEpisodeSynthesis` for that chunk's turns, writes deltas live to the HTTP response, caches the full PCM chunk, bumps `Episode.generatedAudioSeconds`, and proceeds to the next chunk.
     - A follower on the same instance awaits the in-flight generation promise; a follower on another instance polls the cache for that chunk.
  3. Once all chunks are generated and cached, assembles the complete PCM and calls `finalizeEpisodeAudio` to encode `final.ogg` via ffmpeg and clean up temporary guest voices.

Cache layout in Storage: `podcasts/{podcastId}/episodes/{episodeId}/audio/chunk-{index}.pcm` (per-chunk raw PCM) and `.../audio/final.ogg` (the finished episode — meant to expire after 90 days).

`episodeGeneration/` pipeline, in the order `orchestrator.ts` runs them: `speakerSelection.ts` (one-time cast decision) → `scriptGeneration.service.ts` (the single LLM call that writes the whole episode's script itself, parses it into turns via `scriptText.ts`, normalizes speaker labels against the known cast, and rebuilds the canonical transcript via `transcriptBuilder.ts`) That's it — there's no producer-prompt or chunking step anymore (see the Gemini 3.8 Flash TTS migration section above). `voiceResolution.service.ts` and `audioFinalize.service.ts` also live in this folder but aren't run by the orchestrator at all — they're called lazily from `audio.service.ts` (top-level `services/`, not `episodeGeneration/`), the on-demand TTS/streaming layer, the first time a listener actually needs audio (see "Audio delivery" below).

## Running things

```bash
npm run dev      # tsx watch, port from .env (PORT)
npm run build && npm start   # production-ish
npm test         # vitest — fast, no network calls, safe to run freely
npm run smoke    # scripts/smoke-test.ts — full real HTTP flow, costs real Gemini/TTS quota, takes minutes
```

`.env` needs: `FIREBASE_PROJECT_ID` (also used as the Gemini Enterprise project — see Gemini API usage below), `FIREBASE_SERVICE_ACCOUNT_PATH` (local dev only — omit in any deployed environment; see `config/firebase.ts`), `FIREBASE_STORAGE_BUCKET`, `FIRESTORE_DATABASE_ID` (defaults to `podcasts`), `PORT`. Text generation and TTS both authenticate via Application Default Credentials (no API key anywhere). `ffmpeg` (with libopus) must also be installed wherever this runs outside the provided Docker image — it's in the Dockerfile's runtime stage, but local dev needs it on `PATH` separately.

`npm run deploy` (`scripts/deploy.sh`) deploys to Cloud Run via `gcloud run deploy --source`, forwarding `.env` as env vars (minus `PORT`, `FIREBASE_SERVICE_ACCOUNT_PATH`, and anything not read by `config/env.ts`).

**CI deploy (preferred): `.github/workflows/deploy.yml`** deploys on every push to `main` (production `ai-podcast-api`) or `claude-develop` (shared dev service `claude-develop-ai-podcast-api`). To get a live URL for a change, push there instead of running `npm run deploy`:
```bash
git push origin HEAD:claude-develop --force
```
(force, since `claude-develop` is a disposable pointer to "whatever's being tested right now.") It mirrors `rodrigos01/ai-audio-book`'s workflow — same GCP project (`ai-audio-book`), same Workload Identity Federation pool/provider (`github-actions-pool` / `github-actions-provider`), same deploying service account (`player@ai-audio-book.iam.gserviceaccount.com`), no stored key and no GitHub secrets needed. It builds the root `Dockerfile` on the runner with Docker Buildx + the GitHub Actions layer cache, pushes to Artifact Registry (`cloud-run-source-deploy`), and deploys with `--image`, running as the same runtime service account the service already used (`883622140264-compute@developer.gserviceaccount.com`). `FIREBASE_PROJECT_ID` / `FIREBASE_STORAGE_BUCKET` / `FIRESTORE_DATABASE_ID` default to the production values inline and can be overridden via repository **variables** (not secrets — none are sensitive).

For WIF to accept this repo's tokens, the provider's `--attribute-condition` must allow `assertion.repository == 'rodrigos01/ai-podcasts-api'` on `refs/heads/main` / `refs/heads/claude-develop`, and `player@` must grant `roles/iam.workloadIdentityUser` to this repo's `principalSet://.../attribute.repository/rodrigos01/ai-podcasts-api` — both live in the `ai-audio-book` project, shared with the audio-book repo.

**Manual E2E testing convention used throughout development**: start the dev server in the background (`nohup npx tsx src/index.ts > /tmp/....log 2>&1 &`), drive it with `curl` against the real Gemini API, poll `GET .../episodes/:id/status` until `ready`/`failed`. This is real, billed API usage — be deliberate about how often you trigger full episode audio generation while testing; a full episode's script is a couple minutes of wall-clock time, and its audio is now one streaming TTS call for the whole thing (up to ~20 minutes of real generation time for a long episode, per the Gemini 3.8 Flash TTS migration above) — not several small independent chunk calls. Always `fuser -k 3000/tcp` (or kill by PID) before restarting — a half-killed dev server left listening on port 3000 has caused confusing "stale server" debugging sessions before.

## Testing philosophy in this codebase

- **Pure logic gets unit tests** (vitest, `test/`): word counting, speaker-cast selection and label computation (`speakerSelection.test.ts`), the two-voice zod refinement, the episode-suggestions-array shape (`wizard.schema.test.ts`), the free-text voice field, English persona/accent fields and server-managed resolved-voice fields (`person.schema.test.ts`), English-field reconciliation on host edits (`englishFields.test.ts`) and the save-time English-field service (`personEnglish.service.test.ts`), the speaker-label output-format validation (`scriptGeneration.service.test.ts`), Unicode-safe speaker-label parsing (`scriptText.test.ts`), WAV build/extract/byte-offset arithmetic (`wav.test.ts`), speech-part building, same-speaker detection and moderation-keyword matching (`ttsClient.test.ts`), host-voice cache invalidation across the AI Studio→Enterprise move (`voiceResolution.test.ts`), deterministic prompt rendering.
- **Everything touching a real external API (LLM text-gen, TTS, Voice Design/Library, Firestore, Storage, `ffmpeg`) is verified manually against the live services**, not mocked in automated tests — this project has no test-double layer for `@google/genai`, `firebase-admin`, or subprocess encoding. If asked to add automated coverage for those paths, that's new scope, not a gap to silently "fix."
