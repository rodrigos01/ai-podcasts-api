# AGENTS.md

Guidance for AI coding agents working in this repository. Read this before making changes — several things here are non-obvious from the code alone.

## What this is

A REST API backend for an AI-generated podcast app: users create fictional podcast shows (hosts, structure) and episodes (topics, guests, source material), and the app generates an episode's conversation transcript via a single Gemini call, then synthesizes it to audio via Gemini TTS, streamed back to the client. Product behavior is specified in [specs.md](specs.md); the prompting conventions for TTS are in [prompting-guide.md](prompting-guide.md) and [voice-reference.md](voice-reference.md).

**specs.md is the product spec, not the API design.** It's silent on several things this backend had to decide — see "Architecture decisions" below before assuming specs.md is complete on its own.

## Migration from multi-agent to single-LLM script generation (2026-09-21)

Transcript generation used to be two independent LLM calls per turn (one `AgentSession` per speaker, alternating strictly, each with its own private system instruction) — replaced with **one LLM call that writes both speakers' lines itself** ([scriptGeneration.service.ts](src/services/episodeGeneration/scriptGeneration.service.ts), [scriptGeneration.prompts.ts](src/llm/prompts/scriptGeneration.prompts.ts)). This followed a real experiment comparing both approaches on the same live source material (methodology and full results are written up externally, not in this repo): single-LLM was 3.5-5.8x faster wall-clock and, contrary to expectation, produced *more* naturalistic turn pacing than forced per-turn alternation (shorter, choppier, more interruption-like exchanges — see "The conversational-density lesson" below). Two tradeoffs were consciously accepted, not overlooked:

- **No mid-generation word-count checkpoint.** The multi-agent loop's mechanical breaker (the old `conversationLoop.ts`) is gone — a single non-streaming call has no equivalent, and the experiment measured real overshoot (16-43% over target, worse under looser prompting, never fully eliminated by tightening it) because the model tends to track the source material's real scope over the literal word target. Mitigated at the product level instead: target length is now chosen *before* drafting (see point 8 below) and the episode wizard can suggest splitting into two episodes when the target is a genuine mismatch for the material — but there is still no hard guarantee on any single episode's transcript length. A real mid-generation checkpoint (stream the call, inject a forced wrap-up as word count nears the max) was considered and deliberately deferred, not rejected — worth revisiting if overshoot proves to be a real problem in practice.
- **No structural per-speaker knowledge partitioning.** The old pipeline gave each speaker an independent LLM call plus a per-speaker source split (`sourceAssignment.service.ts`, since deleted) so two speakers could never "know" something the other hadn't said aloud, by construction. A single LLM authoring both sides is unavoidably omniscient of everything in the prompt regardless of what the transcript shows — `scriptGeneration.prompts.ts` asks the model to keep the two characters' knowledge and reactions independent, but this is prompting, not a structural guarantee. Treat this as an accepted, permanent characteristic of this architecture, not a bug to fix later.

**Speaker labels are first name only, by contract, with the format validated (not fuzzily resolved) after generation (2026-09-22).** The experiment found stricter word-count prompting made the model drift between full names ("Maya Cruz") and abbreviated ones ("Maya") — since `chunker.ts`/`geminiClient.ts`'s TTS voice assignment key off the exact label string, this used to be handled by a fuzzy resolver (`normalizeSpeakerTurns`, trying exact → case-insensitive → prefix/first-name matching against the known cast) that guessed at what a drifted label "must have meant." That resolver is gone. Instead, [speakerSelection.ts](src/services/episodeGeneration/speakerSelection.ts)'s `speakerLabel(name, otherName)` computes one canonical label per speaker up front — first name only, falling back to the full name only when the two cast members share a first name — and [scriptGeneration.prompts.ts](src/llm/prompts/scriptGeneration.prompts.ts) tells the model to use exactly those two strings, framed as a hard technical requirement (byte-for-byte matching, not a style preference), not merely a naming convention. `scriptGeneration.service.ts`'s `validateSpeakerTurns` then does no resolution at all — it just checks that every parsed turn's label is one of the two expected strings and that both appear at least once, throwing (and letting the caller retry the whole generation — cheap, a single call) if not. The same `speakerLabel` computation is reused in `audio.service.ts`'s `resolveCastVoices` and `producerPrompt.service.ts`, so the transcript's turn labels, the TTS voice-alias mapping, and the producer's own director-prompt labels all agree on the same string. If you're tempted to bring fuzzy resolution back: don't — the whole point of the first-name-only convention is that the format is simple enough to ask for exactly and verify exactly, rather than needing to guess at variations.

**A real, independent bug this surfaced (2026-09-22): [scriptText.ts](src/utils/scriptText.ts)'s label-matching regex was ASCII-only** (`[A-Za-z0-9 .'-]`), so a genuinely correct label containing any accented or non-Latin letter (e.g. "Chloé") failed to match *at all* — not a drift/format issue, a parsing bug. The whole "Name: line" turn silently got folded into the previous turn's text as an unlabeled continuation, and the resulting missing speaker surfaced downstream as "the generated script never gives Chloé Moreau a line," which reads like a model-compliance failure but was actually this regex never recognizing her label in the first place. Fixed with Unicode property escapes (`\p{Lu}`, `\p{L}`, `\p{M}` for a possible NFD-decomposed accent) and the `u` flag on every `RegExp` built from `NAME_PATTERN` — this is a correctness fix independent of the first-name convention above (a first name can be accented too), so don't assume moving to shorter labels alone would have fixed it.

## Architecture decisions not in specs.md

These were made explicitly during development and should be treated as settled unless the user says otherwise:

1. **Firebase Auth is required** (reversed from an earlier "no auth" decision made before the client side existed). Every `/podcasts` route (and everything nested under it) requires a Firebase Auth ID token — see [middleware/requireAuth.ts](src/middleware/requireAuth.ts), which verifies it via `getAuth(firebaseApp).verifyIdToken()` and attaches `req.userId`. Podcasts are scoped by an `ownerId` field set at creation time; [services/podcastAccess.ts](src/services/podcastAccess.ts)'s `requireOwnedPodcast` is the one shared authorization check used by every controller nested under a podcast (sources, episodes, audio) — a podcast that exists but isn't yours is treated identically to one that doesn't exist (404, never 403), deliberately not leaking existence. This backend still uses the Admin SDK exclusively (bypasses Firestore security rules), so `firebase.rules` (gitignored, not in this repo checkout) is enforcing nothing — all authorization happens in application code, and it must mirror what those rules describe (`isOwner` there is the same model as `requireOwnedPodcast` here). `/health` and `/voices` are intentionally left public. The one exception to "auth via header": `.../audio/stream` also accepts `?token=<idToken>` as a query param, since a plain `<audio src>` element can't attach custom headers and specs.md requires that endpoint to work with one.
2. **Firestore subcollections**, not the nested arrays specs.md literally describes: `podcasts/{id}/episodes/{id}` and `podcasts/{id}/sources/{id}` are subcollections. Hosts stay **embedded** on the podcast document (small, bounded ~1-6) — only episodes and sources (unbounded, large text blobs) moved out, to avoid Firestore's 1MiB per-document limit.
3. **Firestore uses a named database, not `(default)`**: set via `FIRESTORE_DATABASE_ID` (currently `podcasts`). See [src/config/firebase.ts](src/config/firebase.ts) — `getFirestore(app, databaseId)`. If you add a new Firestore database or switch projects, this must be created explicitly (`firebase firestore:databases:create`) — it does not exist by default.
4. **Async job pattern for episode generation**: confirming a suggestion returns `202` immediately with every created episode at `status: "generating"`; script generation runs fire-and-forget in-process (no queue/Redis) — see point 8 below for how a 2-episode confirm is sequenced. Unlike the old per-turn pipeline, the transcript is **not** persisted incrementally — it's written by one LLM call ([scriptGeneration.service.ts](src/services/episodeGeneration/scriptGeneration.service.ts)) and only patched into Firestore once that call (plus parsing/normalization) succeeds — see [orchestrator.ts](src/services/episodeGeneration/orchestrator.ts). This means a crash mid-generation now loses the whole not-yet-persisted script, not just an in-flight turn — an accepted tradeoff of the single-LLM migration (see above), not an oversight. There is no automatic resume — `POST .../episodes/:id/regenerate` restarts a single episode from scratch. If you're asked to add real resume-from-partial or a mid-generation checkpoint, that's a legitimate gap, not an oversight. `status` has four values, not three: `"generating"` → `"streamable"` → `"ready"` (plus `"failed"`). The orchestrator flips `"generating"` to `"streamable"` once the script is written and chunked (see point 5 below) — clients polling `GET .../status` should treat `"streamable"` the same as `"ready"` for "go ahead and call `/stream`," and only look for `"ready"` when they specifically need the episode fully finished (e.g. before trusting `condensedSummaries`, or full-seek support once `/stream`'s static-resource fast path kicks in).
5. **The producer/TTS prompt runs *before*, and in parallel with, script generation — it never needed the transcript.** `generateBaseTtsPrompt` ([producerPrompt.service.ts](src/services/episodeGeneration/producerPrompt.service.ts)) builds the base TTS director prompt **entirely programmatically, with no LLM call at all** (changed 2026-09-24) — a fixed generic "Sample Context" delivery instruction, one `### Audio Profile: {label}` block per speaker using their `persona` field verbatim, and a `### Director's note` section with one `Accent: {label} — {accent}` line per speaker who has an optional `accent` field set (see [person.schema.ts](src/schemas/person.schema.ts); `podcastWizard.prompts.ts`/`episodeWizard.prompts.ts` tell the wizard LLM to set it only when a host/guest's persona specifically calls for a distinctive spoken accent, leaving it unset otherwise). This replaced an earlier `generateText`-drafted template (a "# THE SCENE" paragraph plus a per-speaker AUDIO PROFILE + DIRECTOR'S NOTES block covering archetype/style/pacing/accent) after live testing traced a reproducible Vertex AI content-moderation false positive (support code `54702341`) to that template's elaborate, creative-writing-flavored notes prose for one specific speaker — the exact wording was the trigger, not the persona or topic underneath it (isolated via section-by-section bisection: 4/4 clean without that one speaker's notes paragraph, 0/7 with it, same chunk text throughout). A controlled before/after test against that same previously-failing content found the new, much shorter template took the failure rate from 0/7 to roughly 65-75% success — a real reduction, not a full fix (the same generic classifier false positive can still occasionally fire), on top of the existing retry/backoff and per-chunk skip-and-continue behavior (see the Gemini API usage and Audio delivery sections below) — with no quality regression heard on unaffected episodes in the same test. Dropping the LLM call also means this step no longer needs `podcast`/`episode` at all, just the cast's `Speaker[]` (persona + optional accent), and is synchronous. Verified manually against the live API, not covered by an automated test for the TTS-quality/moderation-rate claims specifically — see `producerPrompt.service.test.ts` for the (pure, deterministic) rendering logic that *is* unit-tested. **Chunking happens in one pass, right after the script comes back — not incrementally.** [chunker.ts](src/services/episodeGeneration/chunker.ts)'s `chunkTranscript` is a left-to-right greedy pass over the whole transcript; the old `sealedChunksSoFar` (which sealed boundaries turn-by-turn against a growing transcript) was removed along with the per-turn pipeline it existed for — there's no longer a "still-growing tail" to hold back, since the whole transcript exists before chunking ever runs. `orchestrator.ts` patches `{transcript, ttsChunks, status: "streamable"}` in one write immediately after chunking, before `condenseForAllHosts` runs.
6. **Stateless wizards**: the server persists nothing until final confirm (`POST /podcasts` or `POST .../episodes`). The client round-trips the current draft/options (or, for episodes, the full `suggestions` array — see point 8) payload on every revision call. Confirming is the one place an episode wizard payload does carry structure server-side: `POST .../episodes` takes `{ episodes: [...] }` (1 or 2 entries — a whole suggestion, not a single draft) precisely so the server can create and sequence a split as one unit instead of the client having to orchestrate it.
7. **The episode "2 voices" rule is a hard, always-enforced constraint**, not a default: `participantHostIds.length + guests.length` must equal exactly 2 (zod `.refine` in [episode.schema.ts](src/schemas/episode.schema.ts)). A single-host podcast therefore requires a guest on *every* episode — there is no solo-host mode, and a podcast with >2 hosts requires the client to pick which 2 voices are cast per episode. This is unaffected by the multi-agent-to-single-LLM migration above — it's a TTS-side constraint (`MultiSpeakerVoiceConfig` needs exactly 2), independent of how the transcript is authored.
8. **Episode length word ranges** (specs.md left `long`'s minimum unstated): short 3500-5000, medium 6500-8000, long 8000-9000 — see [constants/lengthRanges.ts](src/constants/lengthRanges.ts). `length` is now chosen by the client on the **first** episode-wizard request (`POST .../episodes/wizard/options`), before any draft is generated, not suggested afterward — there is no more `suggestedLength` output hint (removed 2026-09-21; it briefly existed 2026-09-20 as a post-hoc hint before this change). The wizard's response is always an array of 1-2 `suggestions` ([wizard.schema.ts](src/schemas/wizard.schema.ts)'s `episodeWizardOptionsResponseSchema`), and **each suggestion is independently either a single episode or a 2-episode split — there is no positional convention** (e.g. no "suggestions[0] is always the single-episode option"). A suggestion's shape is fully described by its own `episodes.length`; clients must key off that, never array position. A lone suggestion can itself be a split (e.g. the user's own prompt explicitly asked for the material to be split, or the material is a genuine mismatch for the chosen length) with no separate single-episode option offered at all; a second suggestion, when the drafter includes one, is just a genuinely useful alternative worth presenting side by side (e.g. a tight single episode vs. a fuller two-part treatment) and is *not* required to differ in episode count from the first. This went through two earlier, wrong designs worth knowing about if you touch this again: first a `.check()` refinement in `wizard.schema.ts` hard-rejected any response that didn't match an assumed "entry 0 has exactly 1 episode" convention — broken because that cross-entry rule can't be expressed in Gemini's structured-output schema, so the model routinely violated it (especially on revise) and every violation failed the whole request. That was replaced with a code-level repair step (`episodeWizard.service.ts`'s `normalizeSuggestions`, since deleted) that silently reordered/synthesized suggestions back into the assumed convention — which fixed the crash but was itself wrong, since it *forced* a single-episode option into existence even when the model correctly decided a split was the only sensible suggestion. The current design has no convention left to enforce or repair: `generateSuggestions`/`reviseSuggestions` just return the schema-validated result directly. **Confirming a suggestion (`POST .../episodes`) always takes its whole `episodes` array in one call** ([episodeCreateRequestSchema](src/schemas/episode.schema.ts), `{ episodes: [...] }`, 1 or 2 entries) — not one draft at a time. The controller creates every episode in the array immediately (all returned in the response, all at `status: "generating"`), then hands their ids to `orchestrator.ts`'s `runEpisodeGenerationSequence`, which actually generates them **one at a time, in order**: part 2's script-writing call doesn't start until part 1 reaches `"ready"`, so it naturally inherits part 1's `condensedSummaries` the same way any other follow-up episode would. This sequencing is entirely server-side and transparent to the caller — a client never orchestrates it, and confirming a single-episode suggestion (`{ episodes: [oneDraft] }`) goes through the exact same code path with a 1-element array. If an earlier part in the sequence fails, `runEpisodeGenerationSequence` marks every remaining part `"failed"` too (with an explanatory `error`) rather than leaving them stuck in `"generating"` forever — `/regenerate` still works on any one of them individually afterward. There is deliberately no persisted link between the parts of a split (no `partOf`/`seriesId` field on `Episode`) — grouping is conveyed only through each draft's own title/topics/productionNotes text, and the confirm request's array order.
9. **Firebase Storage bucket must be explicitly linked** to the Firebase project — creating a GCS bucket and pointing `firebase-admin`'s Storage client at it (via `storageBucket` in `initializeApp`) works at the SDK level but does **not** make it appear in the Firebase console's Storage tab. That requires the `firebasestorage.googleapis.com` API to be enabled on the project and the bucket registered via its bucket-management REST API (`POST .../buckets/{bucket}:addFirebase`). Already done for the current bucket (`ai-audio-book-podcast-audio`); if you provision a new bucket, repeat this.

## The conversational-density lesson (read before touching script-generation prompts)

Early testing (on the old per-turn, two-independent-agent pipeline) found that generated transcripts read as a "two-way monologue" — each turn a complete, thorough response — regardless of topic (audio gear, celebrity gossip, marine biology) or format (2 co-hosts, host-interviews-guest). That ruled out topic/format as the cause. The fix was explicit persistent guidance that most turns should be short (a reaction, an interjection, a partial thought), that a turn can be a pure reaction with zero new information, and that a speaker can deliberately leave something unfinished as a hook for the other to ask about — this guidance now lives in [scriptGeneration.prompts.ts](src/llm/prompts/scriptGeneration.prompts.ts)'s `buildScriptSystemInstruction` (carried over from the old per-speaker `hostPersona.prompts.ts`, since deleted). **Do not add example phrases to that guidance** — the user explicitly asked to avoid them since concrete examples bias the model toward reusing those exact words. Interestingly, the single-LLM migration's own experiment found this same guidance produces turns that are *shorter and choppier* than the old forced-alternation pipeline ever managed — a single writer, unlike two independent agents taking strict turns, can freely decide how many turns one "beat" takes instead of front-loading a whole beat into one turn because it doesn't control when it speaks again.

**A real bug from the old pipeline (2026-09-19, still relevant): dialogue occasionally started a new paragraph/line with something shaped like a speaker label** — e.g. "Watch this: it does something wild". `transcriptBuilder.ts` joins turns with `"\n\n"`, and everything downstream (`chunker.ts`, `scriptText.ts`'s `parseScriptTurns`) re-splits on that exact separator to find turn boundaries — so a line landing on "Word:" got misread as a new speaker label, scrambling TTS voice attribution. Still fixed two ways, deliberately not just one: `scriptGeneration.prompts.ts`'s system instruction explicitly tells the model not to open a line (or an internal sentence) with "word:" phrasing, *and* `scriptGeneration.service.ts`'s `sanitizeTurnText` unconditionally collapses any internal `\n{2,}` within a parsed turn's own text into a single space — so the invariant ("a turn's text never contains the turn-boundary separator") holds regardless of whether the model actually complies with the prompt. Don't remove the code-level collapse just because the prompt instruction seems to be working.

**A fourth lesson (2026-09-20, still relevant): agents defaulted to ending most turns with a question** — a recognizable "LLM interview" tic (always fishing for the other speaker's next line rather than just... talking) rather than how real co-hosts actually converse. Fixed with an explicit instruction not to close every turn with a question, while still allowing occasional genuine ones, with one carve-out: a show whose structure/production notes actually call for an interview format should keep asking questions, since that's the correct dynamic there. Verified against a real episode generation on the old per-turn pipeline (co-hosting, not an interview): only 2.2% of turns ended in a question mark — comfortably in "occasional and natural" territory, not the "every turn" pattern that prompted the fix. Re-verify this hasn't regressed if you touch `scriptGeneration.prompts.ts`'s question-ending guidance, since it's now one writer deciding for both speakers rather than two independent agents each separately instructed.

## Gemini API usage — non-obvious things learned the hard way

- **Text generation** (`gemini-3.8-flash`) uses the plain `models.generateContent` API with `responseSchema` built from the same zod schema used to re-validate the output (`toGeminiSchema` in [geminiClient.ts](src/llm/geminiClient.ts) strips `$schema`/`additionalProperties`, which Gemini's schema dialect rejects). Never trust LLM JSON without the zod re-parse.
- **Text generation is routed through the Vertex AI API, not the API-key-based Generative Language API ("AI Studio")** (migrated 2026-09-20). `getClient()` in [geminiClient.ts](src/llm/geminiClient.ts) now constructs `GoogleGenAI` with `{ vertexai: true, project: env.FIREBASE_PROJECT_ID, location: env.VERTEX_AI_LOCATION, googleAuthOptions }` instead of `{ apiKey }` — same `@google/genai` client, same `generateContent`/`generateContentStream`/`countTokens` call sites, no code changes needed anywhere else. Motivation was billing, not quality or capability: AI Studio bills through a separate, pre-paid path, while Vertex bills the same GCP project (standard metered billing, `roles/aiplatform.user` required on the service account) that Firebase Admin and Cloud TTS already use — see `credentials`/ADC note below. **Don't confuse this with the TTS transport decision**: Vertex AI's own `generateContent`-based TTS path was evaluated and rejected (see the `streamSpeech` entry below) — this migration is text-gen only, `GEMINI_API_KEY` is gone from `env.ts` entirely, and TTS stays on `@google-cloud/text-to-speech`.
- **Structured output (`responseSchema`) is real overhead, not free — use `generateText` only when the shape genuinely needs validating.** Confirmed empirically (2026-09-17, 15 real side-by-side trials against the live API with an equivalent short prompt/response): grammar-constrained JSON output ran ~35-55% slower on average than the same call with no schema at all, with a noticeably fatter slow tail (the multi-second outliers were structured-only). The episode script writer ([scriptGeneration.service.ts](src/services/episodeGeneration/scriptGeneration.service.ts)) doesn't need JSON — its output is just the "Name: line" transcript text itself, parsed by `scriptText.ts`'s `parseScriptTurns` — so it uses `generatePlainText` instead. The wizards/`condensation.service.ts` still use `generateText` — their shapes (3 podcast options, nested arrays, etc.) are complex enough that hand-parsing plain text would be more fragile, not faster in any way that matters relative to their call frequency (once per wizard step / once per episode, not once per turn). `producerPrompt.service.ts` used to be in this list too, but as of 2026-09-24 it makes no LLM call at all — see Architecture decision 5 above.
- **TTS (`streamSpeech` in [geminiClient.ts](src/llm/geminiClient.ts)) uses `@google-cloud/text-to-speech`'s `streamingSynthesize` bidi gRPC call, not `@google/genai` at all.** This is a migration (2026-09-16) off two earlier approaches — first `models.generateContent`/`generateContentStream` (one-shot, no real streaming), then the Generative Language API's Interactions endpoint (`client.interactions.create`, genuine streaming but billed through AI Studio's separate pre-paid path) — to Cloud Text-to-Speech, which exposes the *same* `gemini-3.1-flash-tts-preview` model at a much cheaper cost basis, confirmed empirically end-to-end after the switch. Text generation (`generateText`/`countTokens`) went through a separate migration (2026-09-20, see above) onto Vertex AI — still `@google/genai`, just not AI Studio anymore.
  - **Vertex AI's own TTS path (`generateContent`/`generateContentStream` with `speechConfig`, per [Google's docs](https://docs.cloud.google.com/text-to-speech/docs/gemini-tts#use-vertex-ai-api)) was evaluated (2026-09-20) and rejected — don't migrate TTS there without re-litigating this.** It only returns raw PCM (16-bit/24kHz, no WAV header) — confirmed directly from Google's own Vertex code samples, which manually wrap the response bytes in a `.wav` header client-side because there's no encoding option in the request schema (`GenerateContentConfig`/`SpeechConfig` has no `audio_config`/encoding field at all — that's a Cloud TTS-only concept). Moving TTS there would mean losing `OGG_OPUS` entirely (see the size/chunking notes below) — either a new PCM→Opus transcode step, or reworking storage/streaming around much larger raw/WAV audio. No documented quality difference exists between the two paths for the same model, so there's no upside to offset that cost. If a future Gemini-TTS quality issue comes up, check speaker-alias simplicity (see `speakerAlias` note below) before considering this again.
  - Shape: write a `{streamingConfig: {voice: {modelName, multiSpeakerVoiceConfig: {speakerVoiceConfigs: [{speakerAlias, speakerId}]}}, streamingAudioConfig: {audioEncoding, sampleRateHertz}}}` message first, then a `{input: {prompt, multiSpeakerMarkup: {turns: [{speaker, text}]}}}` message, then `.end()` the stream. `prompt` (our director's-brief text, e.g. Scene/Audio Profile blocks) and `multiSpeakerMarkup.turns` are both accepted together on the same input message — confirmed empirically, not assumed from docs.
  - **`streamingSynthesize` only accepts a narrow subset of the API's advertised `AudioEncoding` values.** Confirmed empirically by testing each directly against the live API: `LINEAR16` (the equivalent bit format for the *non*-streaming `synthesizeSpeech` call) and `MP3` are both rejected outright with `INVALID_ARGUMENT: Unsupported audio encoding`, even though both are valid, documented encodings for the API in general. Only `PCM` and `OGG_OPUS` are confirmed to work with the streaming call. Don't assume an encoding works here just because it's a valid `AudioEncoding` enum value — re-test against the live API before relying on a new one.
  - **We use `OGG_OPUS` (migrated 2026-09-16 from `PCM`), not raw PCM, for the roughly 10-16x smaller output** (measured on real generated chunks: e.g. one ~73s chunk went from 3.2MB as PCM to ~300KB as Ogg Opus) — this was the whole point of switching, PCM's size was a real user-facing concern. This forced a real redesign, not just a config flag flip: raw PCM has an exact, constant bytes-per-second relationship that let the old code compute a `?t=<seconds>` resume position with simple arithmetic (`utils/wav.ts`'s `secondsToByteOffset`, now deleted) and prepend a single WAV header (`buildWavHeader`) to the whole concatenated stream. Ogg Opus has neither property — no linear time↔byte mapping, and each chunk is already its own fully self-contained Ogg stream (own header, own final page) straight out of `streamingSynthesize`, so no header-wrapping step is needed *or possible* the same way. See [utils/oggOpus.ts](src/utils/oggOpus.ts):
    - Concatenating multiple chunks' raw bytes still works (unaffected) — this produces a "chained" Ogg bitstream, a legitimate, spec-supported construct that standard players handle. [audioCache.repository.ts](src/storage/audioCache.repository.ts) caches each chunk as a standalone, independently-playable `chunk-N.opus` file (not headerless raw data like the old `.pcm` files were).
    - `?t=<seconds>` resume is now resolved to the nearest **chunk boundary at-or-before** the requested time, not an exact byte offset — `getOggOpusDurationSeconds` recovers a chunk's *real* duration from its final Ogg page's granule position (always in units of 1/48000s for Opus, per RFC 7845, regardless of the stream's actual sample rate), and `resolveTimeToByteOffset` walks cached chunks summing durations until the target time is reached. Confirmed correct via unit tests (real and synthetic Ogg pages) plus a live end-to-end check (a resumed stream's first bytes matched a specific cached chunk's file byte-for-byte). A resume can start up to one chunk's length early, but never skips ahead of where the listener actually left off — exact-second precision is a real gap if you need it later, not an oversight.
    - A `Range` header (an exact byte offset, from a player's own seek) still takes priority over `?t=` — browsers/players handle sub-chunk seeking within a real Ogg resource themselves via their own container parsing once `Content-Length` is known, so we don't need to compute that ourselves.
  - `streamSpeech`'s signature is `(directorPrompt: string, turns: ScriptTurn[], speakers: SpeakerVoice[], onChunk)` — callers pass the prompt and `parseScriptTurns(chunkText)` (in [utils/scriptText.ts](src/utils/scriptText.ts)) separately, rather than concatenating them into one flat string.
  - Credentials: local dev uses the same already-loaded service-account object as Firebase Admin ([config/firebase.ts](src/config/firebase.ts)); in any deployed environment (no `FIREBASE_SERVICE_ACCOUNT_PATH` set) both clients fall back to Application Default Credentials via the runtime's attached service account instead — no key file needed in the image.
  - Retry care: a naive retry-the-whole-call-on-any-error is wrong here, because by the time an error surfaces some audio deltas may already have been written to a live HTTP response via `onChunk` — retrying would duplicate those bytes downstream. `streamSpeech`'s retry loop tracks whether *any* audio was emitted and only retries a clean failure (nothing emitted yet); once any data has gone out, it stops retrying and surfaces the error immediately. Preserve this if you touch it.
  - This also **fixed a real performance problem**, not just cost: the Interactions API took 45-90+ seconds per ~1000-token chunk; Cloud TTS streams comparable audio in a small fraction of that in testing. If synthesis feels unexpectedly slow again, that's a regression, not expected behavior.
  - **`streamingSynthesize` has an undocumented per-call output ceiling.** A single call reliably resets the gRPC connection (`13 INTERNAL: Received RST_STREAM with code 2`) once its own output audio gets long enough — observed consistently at ~178s of audio for a ~950-token chunk, on every retry, never caching any partial output (so this isn't a transient flake to retry around). Confirmed fixed by shrinking `TARGET_CHUNK_TOKENS` (see below) so a chunk's synthesized audio finishes comfortably under that ceiling — re-verified end-to-end afterward with a real episode stream running continuously past the old failure point with zero errors.
  - **`speakerVoiceConfigs[].speakerAlias` must be alphanumeric only — no spaces, apostrophes, or hyphens.** Rejected outright (`"Multi-speaker synthesis requires well structured speaker aliases..."`) for any real display name containing them (e.g. a guest named "Ray Sterling"). Beyond that hard requirement, Gemini TTS's own multi-speaker examples use short single-word aliases (e.g. "Joe") — a sanitized-but-still-multi-word alias (e.g. "DrEmilyChen") is legal but empirically hurts speaker attribution over longer multi-turn scripts (fixed 2026-09-20). `geminiClient.ts` now uses each speaker's assigned voice ID (Puck, Kore, ...) as the wire-format alias instead — already one simple word, and already unique per speaker in a cast thanks to the voice-collision prompt fix above — mapped internally via an `aliasByName` Map. `audio.service.ts` keeps using real display names throughout and never sees this constraint. `sanitizeSpeakerAlias()` remains only as a defensive fallback for a turn whose speaker isn't in the known cast list. Don't bypass this by passing raw speaker names straight through to `speakerVoiceConfigs`/`multiSpeakerMarkup.turns`.
- **A single-speaker chunk + a 2-voice `multiSpeakerVoiceConfig` was a real, reproducible quality bug** (investigated 2026-09-21; briefly "fixed" by raising `TARGET_CHUNK_TOKENS` to 500 specifically to make single-speaker chunks rare — see the constant's own history in [constants/ttsLimits.ts](src/constants/ttsLimits.ts)). Every `streamSpeech` call used to declare *both* cast voices regardless of which speakers actually appeared in that chunk's `turns` (Cloud TTS's `MultiSpeakerVoiceConfig` requires exactly two speaker configs, full stop — you can't just pass one) — a mismatch that produced a real, user-reported artifact: hallucinated lines attributed to the silent voice, degenerate repetition loops, and voice misattribution, confirmed via abnormal per-token pacing (2-3x slower than normal) and by direct listening. Two other explanations were investigated and ruled out first: it is **not** the bidi-vs-unary transport (switching `streamSpeech` to the unary `synthesizeSpeech` call and back reproduced the same artifact, so don't re-attempt that migration for this reason) and it is **not** a chunk-boundary-splits-mid-turn issue.
  - **2026-09-23: `TARGET_CHUNK_TOKENS` moved back to 350** to fix voice-attribution drift instead (Gemini TTS recommends staying under ~3 minutes of audio per call; 500 tokens' 115-125s chunks were already past where drift creeps in) — which makes single-speaker chunks common again. Rather than re-widen the budget to avoid them, `geminiClient.ts`'s `soloSpeakerVoiceName` now detects a single-speaker chunk and routes it through genuine single-voice synthesis (`voice.name` + `input.text`, no `multiSpeakerVoiceConfig`) — the exact fix a 2026-09-21 evaluation of this same approach had rejected, for an observed increase in false-positive content-moderation rejections (support code `54702341`) on plain single-voice requests. That tradeoff is real and confirmed again live (2026-09-23): the single-voice shape does measurably fail more often (moderation false-positives, and separately `RST_STREAM`) than the multi-speaker shape — `isModerationRejectionError` in geminiClient.ts gives that specific failure a longer exponential backoff (mirroring the existing 429 handling) rather than eliminating it. This was an acceptable-but-real risk for most chunks (a failure is silently skipped, see the Audio Delivery section below) until it hit chunk 0 in production — chunk 0 is disproportionately likely to be a solo-speaker kickoff monologue, and its failure used to be unrecoverable (it carried the episode's only Ogg header), turning into a real user-facing 500. Fixed by decoupling the header from chunk 0 entirely (`OGG_HEADER_PAGES`, see Audio Delivery below) rather than avoiding solo-voice for chunk 0 specifically — every chunk's failure, including chunk 0's, is uniformly skippable now.
  - Separately: a well-formed, genuinely multi-speaker chunk can still have the wrong configured voice read a turn (confirmed once in testing, a turn correctly labeled and structured still came out in the other speaker's voice) — this looks like inherent Gemini TTS voice-attribution drift, documented as a known behavior in Google's own docs, not something fixable via chunking or request construction. A real production episode also exhibited outright audio duplication — the *identical* input text produced normal-length audio once and ~2x-duplicated audio another time, via the single-voice path with no second voice declared at all, ruling out the "silent second voice" theory as the sole cause of this class of bug — and, separately again, a genuine infinite repetition loop on an ordinary two-speaker chunk (not solo-voice at all), which motivated `MAX_CHUNK_AUDIO_SECONDS` (see below). Don't mistake a future report of any of these for a regression in a specific fix above — they're documented as inherent, rare TTS-model-level behavior.
- **`countTokens`/text-gen calls are cheap; TTS calls are not quite as slow as they used to be, but still not instant** — budget real wall-clock time when testing audio generation manually, and don't casually re-trigger full episode audio generation while iterating, since it's still billed API usage. `chunker.ts` targets `TARGET_CHUNK_TOKENS` (350, not the much larger `MAX_TTS_INPUT_TOKENS` input ceiling) primarily so audio streaming can start playback quickly, but this number is now also load-bearing for staying under `streamingSynthesize`'s RST_STREAM ceiling above and for keeping the episode's own ~3-minute-per-call recommendation — don't raise it back toward 500 without re-verifying voice-attribution drift, and don't lower it further without re-verifying chunk overhead/latency tradeoffs.
- **Concurrent requests for the same not-yet-generated audio chunk must be deduplicated — across processes, not just within one.** `audio.service.ts` keeps an in-process `Map` of in-flight per-chunk generation promises (`inFlightGenerations`), but that alone only dedupes requests landing on the *same* process — on Cloud Run (or any horizontally-scaled deployment), a second instance has its own empty Map and would happily fire a redundant, costly second TTS call for a chunk the first instance is already generating. `generateOrJoin` adds a Firestore-backed lock on top ([data/audioLock.repository.ts](src/data/audioLock.repository.ts)) — only the instance that wins the lock's transaction actually calls `streamSpeech`; every other instance's local "leader" (first *local* caller for that chunk) polls Storage until the real leader's result is cached, then relays it via a single `onDelta` call instead of generating its own. A lock older than `CHUNK_LOCK_TTL_MS` (5 minutes) is treated as abandoned and stolen by the next waiter, so a crashed leader can't block a chunk forever. Verified against the real Firestore database (not mocked): concurrent acquire attempts on the same key resolve to exactly one winner, a fresh lock blocks further attempts, and an artificially-backdated stale lock gets correctly stolen. If you touch `audio.service.ts`, preserve both layers — the local Map is still worth keeping (skips a Firestore round-trip for the common single-instance case), but the lock is what actually prevents the resource-exhaustion bug across instances.
- **`@google/genai`'s type declarations trip up TypeScript's Node16/NodeNext module resolution** for a plain `import`/`require` (shared `types` field across import/require conditions in its `package.json` exports map, and the package is ESM-first). The fix in use: a dynamic `import("@google/genai")` inside `getClient()`, plus a type-only import guarded with `with { "resolution-mode": "import" }`. Don't "simplify" this back to a static import without re-testing `tsc --noEmit`.
- **Nothing stops the model from assigning two different speakers the same voice ID, unless a prompt explicitly tells it not to** (fixed 2026-09-20). Two separate spots choose voices and both needed the fix independently: [podcastWizard.prompts.ts](src/llm/prompts/podcastWizard.prompts.ts) picks every host's voice in one call (a show with 3+ hosts had real collision risk among them), and [episodeWizard.prompts.ts](src/llm/prompts/episodeWizard.prompts.ts) picks a guest's voice per episode — that one's system instruction *already* listed the show's "Fixed hosts" by name and persona (so the guest wouldn't duplicate a host's *persona*), but never mentioned their voice IDs at all, so the guest step had literally no way to avoid a voice collision with a host. Both prompts now say so explicitly and — for the episode wizard — list each fixed host's voice alongside their persona. Verified against the live API: a 4-host podcast-wizard request (3 options) came back with zero within-option voice collisions, and 3 separate episode-draft requests for guests all avoided both of the show's existing host voices.

## Other gotchas

- **`pdf-parse` v2's API is class-based** (`new PDFParse({ data: buffer }).getText()`), not the v1 `pdf(buffer)` function — don't follow v1-era examples. Use `result.pages[].text` joined with `\n\n`, not `result.text`, which includes ugly `-- N of M --` page markers.
- **`firebase-admin` v14 wants the modular API** (`initializeApp`/`getFirestore`/`getStorage` from `firebase-admin/app`, `/firestore`, `/storage`), not the old namespaced `admin.initializeApp()` style.
- **`dotenv` v17 prints random self-promotional "tips" to stdout on load.** Not a compromise, just noise — suppressed via `dotenv.config({ quiet: true })` in [config/env.ts](src/config/env.ts). Don't reintroduce a bare `import "dotenv/config"`.
- **TypeScript here is v7** (the newer compiler); `moduleResolution` only accepts `node16`/`nodenext`/`bundler` — `"node"` (classic) is gone. This repo uses `module: "Node16"` + `moduleResolution: "Node16"`, which still allows extensionless relative imports for CommonJS output (no `.js` suffix needed), unlike a straight ESM setup.
- **Compound Firestore queries mixing `array-contains` with `orderBy` on another field need a manually-provisioned composite index.** `getRecentCondensedSummariesForHost` in [episode.repository.ts](src/data/episode.repository.ts) deliberately filters in memory instead, to avoid that operational dependency — fine at this app's expected scale (episodes per podcast).
- **Firestore rejects `undefined` field values outright** (throws, doesn't silently drop them). Any optional field must be omitted via spread (`...(x ? {field: x} : {})`), never set to `undefined`.
- **`npm run build` uses [tsconfig.build.json](tsconfig.build.json), not the root `tsconfig.json`, on purpose.** The root config's `rootDir: "."` + `include: ["src", "scripts", "test"]` (so `tsc --noEmit` also typechecks scripts/tests) means a plain `tsc` build emits to `dist/src/index.js`, not `dist/index.js` — silently breaking `npm start`/a deployed container's entry point (`"main"`/`"start"` in package.json both assume `dist/index.js`). This went undetected for a while because local dev always used `tsx` directly, bypassing `tsc` output entirely; it only surfaced when actually deploying. `tsconfig.build.json` narrows `rootDir`/`include` to `src/` only, so `npm run build` produces the right layout. If you ever see "Cannot find module '.../dist/index.js'" after a build, this is almost certainly why.
- **Google Drive sources ([googleDrive.service.ts](src/services/googleDrive.service.ts)) call the Drive v3 REST API directly with plain `fetch`, no `googleapis` SDK** — it's just two GET calls (metadata, then export-or-download), and the caller's own OAuth `accessToken` goes straight through as the `Authorization: Bearer` header; this backend never has Drive credentials of its own and never persists that token. Confirmed empirically against the real API (not assumed from docs): an invalid token genuinely comes back `401` from Drive, and it's mapped to our own `401` rather than leaking Google's error JSON shape — same for `403`/`404`. Google Docs (`application/vnd.google-apps.document`) must be exported (`/export?mimeType=text/plain`); the raw `alt=media` download only works for already-binary files like PDFs (`extractPdfText` reused unchanged). Any other mimeType is rejected with `400`. Like `geminiClient.ts`, this has no automated tests — it's a thin wrapper around a real external API, verified manually (only the error-mapping path is practical to verify without a real Drive OAuth token in hand; the Docs-export and PDF-download success paths still need a real token + file to confirm against, not yet done).

## Audio delivery (`/stream`)

`GET /podcasts/:podcastId/episodes/:episodeId/audio/stream` serves the episode's audio as **one continuous Ogg Opus resource** — not the discrete per-chunk endpoints an earlier version of this API had. See [audio.service.ts](src/services/audio.service.ts) for the full logic; the short version:

- **The gate is `assertAudioAvailable`, not "episode status is ready."** It only rejects `status: "failed"` or a missing `ttsPrompt` (set before the conversation even starts — see the "Architecture decisions" section above). A `"streamable"` episode (at least one chunk sealed, per point 4/5 above) streams normally; a `"generating"` episode with no chunks sealed yet has nothing to serve and is rejected the same as `"failed"`.
- If the episode has finished (`status: "ready"`) and every chunk is already cached in Storage: serves a normal static resource (`Content-Length`, `Accept-Ranges: bytes`, honors any `Range` request — full seek support). A `"streamable"` episode never takes this path even if everything sealed *so far* happens to be cached, since more chunks may still be coming and the total length isn't known yet.
- Otherwise: serves `Transfer-Encoding: chunked` (no `Content-Length`), generating and caching each uncached chunk live via `streamSpeech`, writing Ogg Opus bytes to the response as they arrive.
- **Each chunk arrives from Cloud TTS as its own independent Ogg Opus logical bitstream** (own `OpusHead`/`OpusTags`, own serial number, own granule timeline from 0) — `streamingSynthesize` caps a single call at ~178s of audio (undocumented, empirically found), so this is unavoidable for anything longer. Naively concatenating those, as an earlier version of this endpoint did, produces a "chained" Ogg bitstream that's fragile in practice (even ffmpeg's demuxer errors at each boundary; Android's ExoPlayer doesn't support chaining at all). [utils/oggStitch.ts](src/utils/oggStitch.ts)'s `OggStitcher` rewrites each chunk's pages in place as they're generated — drops *every* chunk's own `OpusHead`/`OpusTags` (chunk 0 included, since 2026-09-23 — see below), unifies the serial number, continues the page sequence/granule timeline, sets `EOS` only on the true final page — so what's cached and relayed is always a fragment of one continuous, non-chained logical stream. No re-encoding, just header/CRC patching on the same Opus bytes.
- **The episode's Ogg header is not derived from any chunk at all (2026-09-23).** `OGG_HEADER_PAGES` in [utils/oggStitch.ts](src/utils/oggStitch.ts) is a fixed, hardcoded `OpusHead`+`OpusTags` page pair, captured once from a real `streamingSynthesize` response — confirmed empirically that Cloud TTS's header payload (channel count, pre-skip, sample rate, vendor string) and even its serial number/page sequence numbers are byte-for-byte identical across every call, since they only depend on the fixed request config (`audioEncoding: "OGG_OPUS"`, `sampleRateHertz: 24000`), never on the synthesized content. `streamEpisodeAudio` writes these exact bytes once, unconditionally, before any chunk synthesis starts (never for a real `Range` request — see below); every chunk, chunk 0 included, is now structurally identical to every other chunk, with no first-chunk special case anywhere in `OggStitcher` or `audio.service.ts`. This replaced an earlier design where chunk 0's own real synthesis output *was* the episode's header, which made chunk 0's TTS failure catastrophic (see the next bullet's history) in a way no other chunk's was.
- **While the episode is still in progress (`"generating"` or `"streamable"`)**, once this request has generated audio for every chunk sealed as of its last look, it re-fetches the episode doc (polling every `EPISODE_CHUNK_POLL_INTERVAL_MS`, [constants/ttsLimits.ts](src/constants/ttsLimits.ts)) and waits for the orchestrator to seal more, rather than ending the response. A listener who starts playback seconds into generation rides straight through into newly-generated audio on the same connection. The loop only stops once status becomes `"ready"` (nothing left to wait for) or `"failed"` — it deliberately checks for those two terminal statuses rather than `=== "generating"`, so it doesn't mistake the `"streamable"` transition for "done." A chunk generated before `status` has confirmed `"ready"` is never trusted as the episode's true final chunk (sealing always holds back the still-growing tail), so its `EOS` bit stays cleared even if it's the last one sealed *so far* — a narrow, cosmetic gap (stream termination doesn't depend on it) rather than a fix-it-now bug.
- **A chunk whose TTS generation fails is skipped, not fatal** (2026-09-20) — most commonly a false-positive content-moderation block on some turn's text, a known Cloud TTS behavior, but the handling is generic to any failure. `streamEpisodeAudio`'s per-chunk try/catch logs the error and moves on: nothing gets written for that chunk (a small silent gap in the finished audio) and nothing gets cached, so a later request tries generating it fresh. **Chunk 0 used to be the one exception** — it used to be the only chunk carrying the episode's Ogg header, so skipping it would've produced a headerless, unplayable stream rather than a content gap, and its failure was re-thrown instead (ending that request's response as a real error). That exception is gone as of 2026-09-23: since the header is now the fixed `OGG_HEADER_PAGES` constant (see the bullet above), not derived from chunk 0's own output, chunk 0's failure is exactly as skippable as any other chunk's — this also fixed a real production issue, where chunk 0 (disproportionately likely to be a solo-speaker kickoff monologue, and therefore routed through the less-reliable single-voice TTS path — see `soloSpeakerVoiceName` in geminiClient.ts) failing surfaced as a 500 far more often than any other chunk's failure did. When skipping a chunk that was this request's own "leader" (see `generateOrJoin`), the catch block calls `stitcher.endChunk()` itself — `generateOrJoin`'s own call to it was never reached — committing whatever partial granule progress happened (0 if the failure hit before any audio arrived, more if some pages were already relayed to the client before it failed) so the *next* chunk's timeline stays correct either way. Verified directly against `OggStitcher` (`test/oggStitch.test.ts`'s two "skipped chunk" tests) for both cases, not just reasoned about.
- **A single TTS call's synthesized audio is capped at `MAX_CHUNK_AUDIO_SECONDS` (180s, [constants/ttsLimits.ts](src/constants/ttsLimits.ts); 2026-09-23).** Confirmed live in a real production episode: Gemini TTS's documented "degenerate repetition loop" behavior can mean a chunk just never stops generating — no error, no natural end-of-stream — which without a cap streams to a live listener indefinitely. `generateOrJoin` tracks the *in-progress* chunk's own duration via `OggStitcher.getCurrentChunkSeconds()` (distinct from `getCumulativeSeconds()`, which only advances once a chunk fully finishes via `endChunk()`) and throws once it exceeds the cap, from inside `streamSpeech`'s own `onChunk` callback — the same mechanism that already turns a thrown callback error into a clean rejection (see the uncaught-exception fix below) — so a killed chunk goes through the exact same retry/skip handling as any other TTS failure.
- **The actual mechanism behind "TTS errors crash the server" (fixed 2026-09-20, same date) was almost certainly not Cloud TTS's own error path** (that already rejects cleanly via the gRPC stream's `"error"` event) **but our own delta-processing code throwing.** `generateOrJoin`'s `onDelta` callback (Ogg page reassembly + stitching) used to run synchronously inside `streamSpeech`'s `"data"` event handler in [geminiClient.ts](src/llm/geminiClient.ts), *outside* the `new Promise` executor's own call stack — a throw there (e.g. a stitcher invariant violation) escaped as a raw uncaught exception deep inside the gRPC transport's dispatch, not a normal promise rejection, landing only on `index.ts`'s last-resort `process.on('uncaughtException')` handler — which explicitly is *not* safe to resume normal operation after, per Node's own docs. Fixed by wrapping that callback invocation in try/catch and converting a thrown error into a clean `reject()`, same as any other TTS failure. Confirmed empirically, not just reasoned about: a real `streamSpeech` call against the live API with an `onChunk` that deliberately throws now rejects cleanly (`"Cloud TTS stream failed: ..."`) with zero `uncaughtException` firing, where before this fix it would have. If you ever add more processing inside that callback, it's now safe by construction — but don't add new work to the `"data"`/`"error"`/`"end"` handlers themselves without keeping it inside (or covered by) that same try/catch.
- **`?t=` used to silently not work at all — the resumed stream always played from the beginning** (fixed 2026-09-20, superseded 2026-09-23). Root cause was in the old `writeChunk` (since deleted): chunk 0's OpusHead/OpusTags header was only ever carried in chunk 0's own cached buffer, and needed to be injected unconditionally whenever a `?t=`-resolved seek landed *past* chunk 0's start — but the old code only injected it when the seek target landed *inside* chunk 0's own small header region specifically (`start < headerEnd`). Any real seek — landing well past chunk 0, into some later chunk entirely, which is the overwhelmingly common case since chunk 0 is short — fell through to plain byte-slicing that correctly skipped chunk 0's own bytes but never emitted the header at all. This entire class of bug is now structurally impossible: since the header is the fixed `OGG_HEADER_PAGES` constant (see above), it's written once, unconditionally, before any chunk-space byte slicing even begins — there's no "did the seek land past the header" conditional left to get wrong. Verified against a live stream at the time: a `?t=120` request's first audio page had a granule position of ~87s (the correct nearest chunk boundary at-or-before 120s) instead of 0.
- A `Range: bytes=N-` request resumes from byte `N`: if `N` falls in the already-cached prefix, serves precisely from there; if it falls into ungenerated territory, generates that chunk (from its own start) but only starts writing to *this* response once enough bytes exist to reach `N` — the chunk still gets cached in full regardless. A real `Range` header always gets the full body from byte 0 in the not-fully-cached branch, though — there's no valid `Content-Range` without a concrete end position, so honoring the header status-code-wise (`206`) while skipping ahead would break clients (like ExoPlayer) that self-skip based on status code. `N` is in *full-resource space* (header + chunks, what the client actually received) since the fixed header became independent of chunk 0 (2026-09-23) — the fully-cached branch converts it to chunk-space (`N - OGG_HEADER_PAGES.length`, clamped to 0) before slicing the concatenated cached chunk bytes, and never re-writes the header for a real `Range` request (the client already parsed the format earlier in the same logical connection). Only `?t=`'s resolved offset (already chunk-space, no such protocol contract) can start the body elsewhere, with the header written unconditionally first.
- Per specs.md's "Audio Delivery" section: scrubbing ahead of what's been generated is intentionally not supported — this now also means ahead of what's been *sealed*, not just synthesized, while an episode is still generating/streamable. Once every chunk exists, playback behaves like a normal seekable file.
- A `?t=<seconds>` query param lets a client resume by saved playback time instead of a raw byte offset — resolved to the nearest **chunk boundary at-or-before** that time (see [utils/oggOpus.ts](src/utils/oggOpus.ts)'s `resolveTimeToByteOffset`), not an exact byte offset — compressed chunks don't have PCM's fixed bytes-per-second relationship. An actual `Range` header on the same request takes precedence if both are present. Both are resolved against the chunks sealed at request time, same caveat as scrubbing above.
- `Episode.generatedAudioSeconds` tracks total audio duration generated/cached so far, updated in Firestore once per chunk right after it actually finishes generating (`bumpGeneratedAudioSeconds` in [episode.repository.ts](src/data/episode.repository.ts), called from `generateOrJoin` in audio.service.ts) — not computed at request time. It only ever moves forward (a transaction guards against a stale write landing after a later chunk's, though chunk generation is already causally ordered so this shouldn't happen in practice). Included in `GET .../status` and anywhere else the full episode is returned; there's no client-facing "how much is buffered" scrub UI built on top of it yet, but this is the field to build one against instead of computing anything at request time or client-side. Episodes created before this field existed simply don't have it in Firestore (no backfill) — treat a missing/`undefined` value as `0`.

Cache layout in Storage: `podcasts/{podcastId}/episodes/{episodeId}/audio/chunk-{index}.opus` — each entry is a **fragment of the one continuous stitched Ogg Opus stream** described above, not a standalone playable file on its own (no chunk carries a header, chunk 0 included, since 2026-09-23 — see above); concatenating `OGG_HEADER_PAGES` followed by the cached chunks in order reconstructs that one stream.

## Project structure

```
src/
├── config/          — env validation, Firebase Admin SDK init
├── routes/          — Express route wiring (thin)
├── controllers/      — request/response glue (thin)
├── services/
│   ├── podcastWizard.service.ts, episodeWizard.service.ts, source.service.ts, audio.service.ts
│   └── episodeGeneration/   — the single-LLM script generation pipeline (see below)
├── llm/
│   ├── geminiClient.ts      — the only place @google/genai is imported
│   └── prompts/             — one file per prompt-building concern
├── data/            — Firestore repositories (one per top-level/subcollection resource)
├── storage/         — Firebase Storage (audio cache)
├── schemas/         — zod schemas; source of truth for types AND validation AND Gemini responseSchema
├── constants/        — voices.ts (30 prebuilt voice IDs), lengthRanges.ts
├── middleware/, utils/
```

`episodeGeneration/` pipeline, in the order `orchestrator.ts` runs them: `speakerSelection.ts` (one-time cast decision) → `producerPrompt.service.ts` (TTS base prompt, built programmatically from each speaker's persona/accent — no LLM call, no transcript needed, runs independently of script generation) → `scriptGeneration.service.ts` (the single LLM call that writes the whole episode's script itself, parses it into turns via `scriptText.ts`, normalizes speaker labels against the known cast, and rebuilds the canonical transcript via `transcriptBuilder.ts`) → `chunker.ts`'s `chunkTranscript` (one full pass over the whole transcript, once the script comes back) → `condensation.service.ts` (continuity for next time). `audio.service.ts` (top-level `services/`, not `episodeGeneration/`) is the on-demand TTS/streaming layer — it no longer waits for `status: "ready"`, since chunks are available for it to generate audio from as soon as the episode is `"streamable"` (see "Audio delivery" below).

npm run build && npm start   # production-ish
npm test         # vitest — fast, no network calls, safe to run freely

For WIF to accept this repo's tokens, the provider's `--attribute-condition` must allow `assertion.repository == 'rodrigos01/ai-podcasts-api'` on `refs/heads/main` / `refs/heads/claude-develop`, and `player@` must grant `roles/iam.workloadIdentityUser` to this repo's `principalSet://.../attribute.repository/rodrigos01/ai-podcasts-api` — both live in the `ai-audio-book` project, shared with the audio-book repo.

**Manual E2E testing convention used throughout development**: start the dev server in the background (`nohup npx tsx src/index.ts > /tmp/....log 2>&1 &`), drive it with `curl` against the real Gemini API, poll `GET .../episodes/:id/status` until `ready`/`failed`. This is real, billed API usage — be deliberate about how many full episodes/audio chunks you generate while testing; a full episode is 5-10 minutes of wall-clock time and multiple LLM + TTS calls. Always `fuser -k 3000/tcp` (or kill by PID) before restarting — a half-killed dev server left listening on port 3000 has caused confusing "stale server" debugging sessions before.

## Testing philosophy in this codebase

- **Pure logic gets unit tests** (vitest, `test/`): word counting, speaker-cast selection and label computation (`speakerSelection.test.ts`), the two-voice zod refinement, the episode-suggestions-array shape (`wizard.schema.test.ts`), the speaker-label output-format validation (`scriptGeneration.service.test.ts`), Unicode-safe speaker-label parsing (`scriptText.test.ts`), the transcript chunker, deterministic prompt rendering.
- **Everything touching a real external API (LLM text-gen, TTS, Firestore, Storage) is verified manually against the live services**, not mocked in automated tests — this project has no test-double layer for `@google/genai` or `firebase-admin`. If asked to add automated coverage for those paths, that's new scope, not a gap to silently "fix."
